# Контракт: постоянная связь клиента с мастером

Статус: реализовано в `backend/work` (`62fa9d3`) и `master-app/work`
(`44e98b4`); production и deployment не подтверждены.

Backend владеет связью, областью организации, правами и аудитом. Приложение
мастера читает безопасную проекцию. Будущие денежные правила и административное
исправление используют этот источник только после отдельного решения владельца.

## Инварианты

- Новая карточка клиента, созданная мастером, один раз связывается с этим
  мастером с источником `master_created`.
- Найденный существующий клиент автоматически не закрепляется. Дедупликация по
  телефону не даёт права присвоить существующую карточку.
- У клиента может быть не более одной действующей постоянной связи. Мастер не
  может удалить, перенести или перезаписать чужую связь.
- Повторная запись и последующие визиты читают существующую связь, но не меняют
  её.
- Master API возвращает только состояние относительно текущего мастера:
  `mine`, `unassigned` или `other_master`. Идентификатор другого мастера наружу
  не выдаётся.
- Связь не расширяет видимость персональных данных клиента и не даёт доступ к
  чужим визитам. Это происхождение клиентской связи, а не разрешение доступа.
- Само состояние ownership не выбирает ставку и не является формулой оплаты.
  Деньги по-прежнему считает backend по отдельно утверждённому правилу.

## Открытые решения

- Кто и по какому основанию исправляет ошибочное закрепление.
- Нужен ли для исправления отдельный CRM-процесс и какой аудит он оставляет.
- Как ownership влияет на оплату мастера. До решения владельца интерфейс не
  выводит финансовых следствий из этого признака.

## Доказательства и границы

Миграция backend создаёт append-only таблицу с уникальностью клиента; master API
не раскрывает чужой `staff_id`. Проверены создание нового клиента, сохранение
связи при повторной записи, существующий клиент без связи и конфликт с другим
мастером. Это доказательство реализации на указанных SHA, не живой production-
сценарий.
