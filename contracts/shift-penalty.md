## Ручка

```
POST /v1/processes/{process_id}/penalties
X-Actor-Id: <id управляющего>        обязателен
X-Actor-Name: <имя управляющего>     обязателен
```

Адрес карточкой, а не мастером, — намеренно: штраф без карточки в этой
постановке не существует, а `/v1/processes/{id}/…` — уже принятый в продукте
путь действий над карточкой.

**Запрос** (`extra='forbid'`, как все write-ручки):

```json
{
  "penalty_type_id": "3f2a…",
  "quantity": 1,
  "comment": "не закрыл смену, место оставлено грязным",
  "actor_role": "manager",
  "idempotency_key": "shift-penalty:<process_id>:<локальный id нажатия>"
}
```

- `quantity` — целое ≥ 1, по умолчанию 1. Это твоё «если надо, количество»:
  один и тот же вид нарушения бывает кратным.
- `comment` — до 1000 символов, необязателен.
- `actor_role` — `manager` или `owner`. Мастер и администратор штраф не
  выписывают.
- **Рублей в запросе нет вообще.** Фронт передаёт вид и количество, деньги
  считает бэкенд — как ты и просил.

**Ответ 201:**

```json
{
  "id": "9c1e…",
  "process_id": "…",
  "staff_id": "…",
  "penalty_type": { "id": "3f2a…", "name": "Опоздание на смену", "points": 5 },
  "quantity": 1,
  "points_total": 5,
  "amount_rub": null,
  "amount_known": false,
  "comment": "…",
  "issued_by_id": "…",
  "issued_by_name": "…",
  "issued_at": "2026-08-16T19:40:11+03:00"
}
```

`points_total = points × quantity`, посчитан на бэкенде.

`amount_rub: null` + `amount_known: false` — **пока владелец не ответил на твой
вопрос про деньги**. Это не заглушка, а канон: «нет расчёта → прочерк, не ноль»
(`backend/AGENTS.md`, деньги). Ноль здесь означал бы «посчитали, штраф ничего не
стоит» — неправда. Когда ответ будет, поле начнёт возвращать сумму, а
`amount_known` станет `true`; форма ответа не изменится, фронт переписывать не
придётся.

**Повтор с тем же `idempotency_key` → 200 и ТА ЖЕ строка**, второго штрафа не
появляется. Ключ хранится в строке под уникальным индексом — это уже принятый в
продукте способ (`earnings`: выплаты и корректировки живут так же), и он
надёжнее «не жать дважды» на фронте.

**Отказы:**

| код | когда |
|---|---|
| 422 | нет `X-Actor-Id`/`X-Actor-Name` — штраф без имени выписавшего не принимается (в контракте стояло 400; проверено в сборке — платформа отвечает 422 на отсутствующий обязательный заголовок) |
| 404 | нет карточки или вид нарушения снят/не найден |
| 409 | карточка не в `manager_review` — на других шагах штраф не выписывается |
| 422 | `quantity` < 1, роль не `manager`/`owner`, лишние поля в теле |

## Где живёт факт

Новая таблица `staff_penalties`, аддитивная миграция (следующий свободный
номер, `down` возвращает состояние до неё):

| колонка | смысл |
|---|---|
| `id` | |
| `process_id` → `processes` | карточка, по которой выписан |
| `staff_id` → `staff` | кому |
| `penalty_type_id` → `penalty_types` | какой вид |
| `points_each` | **снимок** баллов вида на момент выписки |
| `quantity` | сколько раз |
| `comment` | текст управляющего |
| `issued_by_id`, `issued_by_name` | актор, обе NOT NULL |
| `issued_at` | момент |
| `idempotency_key` | уникальный индекс |

Снимок `points_each` — не дублирование справочника, а защита истории:
справочник правят из CRM, и без снимка вчерашний штраф завтра пересчитается
задним числом. Название вида не копируем — оно берётся по связи, и
переименование должно доезжать до старых записей (правило «названия дословно»).

Индексы: уникальный по `idempotency_key`, обычные по `(staff_id, issued_at)` —
для будущего экрана мастера и зарплаты — и по `process_id` — для карточки.

## След на карточке

Строка в `process_events` тем же запросом: `kind='penalty'`, актор —
управляющий, `message` вида «Штрафные баллы: Опоздание на смену — 5 (×1)» плюс
комментарий. Следующий проверяющий видит, за что.

**Требуется расширить CHECK** `process_events_kind_known` (ревизия 0043) на одно
значение. Миграция обратимая, данных не трогает — по уставу такую согласуешь ты,
владельца не беспокоим. Альтернатива без миграции — писать `kind='comment'`, но
тогда фронт не отличит штраф от реплики в обсуждении, и на карточке он потеряется.

`critical` ставлю **false**: критическим у нас помечено то, что случилось само и
требует разбора (перескок платформы). Штраф выписан человеком осознанно и в
разборе не нуждается. Если фронту нужно выделять его на карточке — это цвет по
`kind`, а не флаг критичности. Спорно — скажи, поменяю в контракте, а не в коде.

## Развилка владельца про деньги — контракт держит оба ответа

v1 **денег не двигает**, как ты и написал. Что будет дальше:

- **«Балл копится»** — зарплата за период читает `staff_penalties` и умножает
  на ставку **на момент расчёта**. Ручка не меняется вообще.
- **«Сразу в деньги»** — тем же запросом создаётся строка в существующих
  корректировках (`payroll adjustments`), а в `staff_penalties` добавляется
  ссылка на неё (одна аддитивная колонка). `amount_rub` перестаёт быть
  прочерком. Ветка становится денежной со всеми последствиями канона: красная
  `money_check.py` блокирует мерж, прогоняет не автор.

Ни один из ответов не требует переделывать форму запроса и ответа — поэтому
фронт можно рисовать, не дожидаясь Кирилла.

## Отмена штрафа — в v1 (правка архитектора 16.08.2026)

Довод принят: система, которая умеет выписать штраф и не умеет его снять,
рождает спор, который нечем закрыть.

```
POST /v1/processes/{process_id}/penalties/{penalty_id}/cancel
{ "reason": "выписала не тому мастеру", "actor_role": "manager",
  "idempotency_key": "…" }
```

Ответ 200 — тот же `PenaltyView`, где `cancelled: true`, `cancelled_at`,
`cancelled_by_name`, `cancel_reason`. Снятый штраф остаётся в списке карточки:
исчезнув, он превратился бы в «мне выписали и тихо убрали».

- Отмена — **новая строка** в той же таблице со ссылкой `cancels_id` и
  причиной, без полей штрафа: она не второй штраф, и дублировать в ней баллы
  значило бы получить строку, которую случайный `sum()` посчитает настоящей.
- **Дважды не отменяется** — уникальным индексом по `cancels_id`, а не
  проверкой в сервисе: между проверкой и вставкой помещается второй запрос.
  Повтор ТОГО ЖЕ нажатия (тот же ключ) отвечает 200 и той же картиной, вторая
  отмена другим ключом — 409.
- **Снимает тот, кто выписал, или владелец** (`actor_role: "owner"`); чужой
  управляющий получает 409. Политику владелец потом сузит — механизм заложен.

## Дыра, которую v1 оставляет сознательно

Штраф выписывается только на шаге `manager_review`. Значит **нарушение,
всплывшее ПОСЛЕ завершения смены — например, следующий мастер сообщает, что
место оставили грязным, — сегодня выписать нечем вовсе.** Это не забытый
случай, а осознанная граница v1; архитектор выносит её владельцу отдельно.

## Чего в контракте сознательно нет
1. **Показа фактов мастеру.** `GET /v1/master/penalties` сегодня честно отдаёт
   только тариф. Когда факты появятся, туда добавится их список — отдельным
   заходом, не в этой ручке.
2. **Штрафа без карточки** (просто «мастеру пять баллов»). Не проектирую: в
   постановке такого нет.

## Что нужно от фронта

Ничего, кроме вида и количества: справочник он уже читает через
`GET /v1/penalty-types`, там же лежит цена балла для показа тарифа. Считать
рубли на экране не нужно и не выйдет — стоимость зависит от грейда мастера.
