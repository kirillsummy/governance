# Контракт: график мастера, ёмкость мест и исход записи в YClients

Технический контракт стыка backend ↔ master-app ↔ YClients для правки графика
мастера ([SUM-115](https://summy.youtrack.cloud/issue/SUM-115), сводная
[SUM-116](https://summy.youtrack.cloud/issue/SUM-116)). Закрывает вопрос 5
(A10 / T17) [SUM-97](https://summy.youtrack.cloud/issue/SUM-97): решение
делегировано Claude в голосовом обсуждении 01.10.2026, новые бизнес-правила
этим документом не вводятся.

## Принятые бизнес-рамки (не меняются здесь)

- 28.09.2026, SUM-96 / P17: соответствие услуги месту берётся из YClients; для
  записи одновременно свободны время мастера и подходящее место; мастер
  открывает время в любой подходящей точке без персонального допуска;
  основное расписание пока в YClients.
- 30.09.2026 ([SUM-115 7-450](https://summy.youtrack.cloud/issue/SUM-115#focus=Comments-7-450.0-0),
  [7-466](https://summy.youtrack.cloud/issue/SUM-115#focus=Comments-7-466.0-0),
  [SUM-97 7-468](https://summy.youtrack.cloud/issue/SUM-97#focus=Comments-7-468.0-0)):
  ёмкость — уникальные физические места с проверенной вместимостью, без
  суммирования групп; прямые правки и записи в YClients остаются; строгая
  гарантия места на весь день **не заявляется**; график сохраняется с
  предварительным статусом ёмкости, предупреждением и сверкой конфликтов;
  QR подтверждает фактическое место в начале смены.

## Решение

Один путь записи, без нового контура состояний. Существующий журнал
`schedule_day_commands` (состояния `reconciling`, `confirmed`, `conflict`) и
поле дня `reservation_state` (`none`, `unverified`, `pending_reconciliation`,
`conflict`) — единственная модель исхода. Код: backend `dbc52d0`, `ff2facc`
(SUM-115), уточнение повтора `2f6487e`; master-app `be8e260`.

### Порядок команды

1. master-app отправляет `requestId` (UUID нажатия) с каждой правкой дня,
   закрытием дня и закрытием промежутка. С 04.10.2026 (R77, SUM-97 № 5)
   `requestId` обязателен: без него `POST /v1/schedule/day/{day}` и
   `/close-interval` отвечают 422 `request_id_required` (backend `e5fe9bb6bc685819bedd702d63dbce0d0056950b`).
2. Backend под advisory-lock мастера и дня проверяет ключ: тот же `requestId`
   с другим составом — 409 `idempotency_conflict`.
3. Для новой команды под advisory-lock `capacity:<location>:<day>`:
   соответствие услуг местам (`resource_mapping_unverified`), блокирующие
   записи, локальная предварительная проверка ёмкости по зеркалу SUMMY
   (`resource_capacity_conflict`, `occupancy_unverified`). Отказ здесь — до
   любой записи в YClients.
   **С 08.10.2026 решением владельца** ([SUM-115 7-1131](https://summy.youtrack.cloud/issue/SUM-115#focus=Comments-7-1131.0-0))
   соответствие услуг местам и проверка ёмкости при открытии и расширении дня
   мастером (и при одобрении заявок управляющей через тот же путь) отключены
   настройкой backend `MASTER_OPEN_DAY_CAPACITY_CHECK_ENABLED` (по умолчанию
   `false`). Причина: проверка не учитывает записи клиентов, держит за мастером
   место каждого типа его услуг на весь график и отказывала при свободных
   местах. Проверка блокирующих записей мастера остаётся. Модуль ёмкости
   сохранён для практических проверок и доступности места в CRM; вернуть
   проверку — `true` без выпуска.
4. Команда сохраняется в журнал в `reconciling` и фиксируется; затем один PUT
   в YClients и GET факта. Ошибка PUT не повторяется автоматически.
5. Если факт YClients совпал — зеркало дня обновляется, команда `confirmed`.
   Не совпал или не прочитан — исход неизвестен.

### Ответы

| Ответ | Смысл | Что делает клиент |
|---|---|---|
| 200, `reservation_state = unverified` | Записано и подтверждено чтением YClients; ёмкость проверена только по зеркалу SUMMY — предварительно | Показать сохранённый день с предупреждением |
| 200, `none` | День закрыт / пуст | — |
| 409 `external_result_unknown` + `requestId` | Команда в `reconciling`: PUT мог дойти или нет | Показать «сверяется»; повторять **тем же** `requestId` (`action: reconcile`), новый ключ на этот день не создаётся — backend отклонит его той же причиной |
| 409 `external_conflict` + `requestId` | Факт YClients разошёлся с командой дольше 10 минут; создан `data_quality_issues.schedule_external_conflict` | Показать конфликт; правка — новой командой после сверки |
| 409 `resource_capacity_conflict`, `resource_mapping_unverified`, `occupancy_unverified` | Отказ до записи в YClients; при открытии дня — только при `MASTER_OPEN_DAY_CAPACITY_CHECK_ENABLED=true` | Объяснить причину, ничего не сохранено |
| 409 `idempotency_conflict` | Ключ уже использован для другого состава | Создать новый ключ только для новой правки |
| 422 / 403 | Неверный запрос / нет права | — |

Отдельного 202 нет: master-app уже различает исход по `detail.reason`, а
второй код для того же состояния создал бы второй контур.

### Повтор запроса

- Повтор `requestId` подтверждённой команды возвращает сохранённый результат
  без повторной записи и без нового чтения YClients. Позднее расхождение с
  YClients показывает сам день: `reservation_state = conflict`.
- Повтор команды в `reconciling` не повторяет PUT: только читает факт и
  подтверждает либо снова отвечает «неизвестно».
- Повтор команды в `conflict` отвечает 409 `external_conflict`; такая команда
  больше не подтверждается.

### Граница гарантии

- Проверка ёмкости локальная и предварительная: независимые записи и правки в
  YClients ею не контролируются, поэтому подтверждённый день означает
  «записано в YClients и прошло проверку по нашему зеркалу», а не
  гарантированное место на весь день.
- Конфликт ёмкости, обнаруженный после записи, — предмет сверки
  (`data_quality_issues`), а не автоматической отмены записей клиентов.
- Записи клиентов (orders, CRM, YClients) этим guard не блокируются: строгую
  гарантию владелец снял 30.09.

## Ёмкость и загрузка филиалов: `GET /v1/staff-capacity` (SUM-220 п. 30)

Разрез только для чтения для CRM («Сотрудники → Структура» и дашборд
управляющего): физическая ёмкость → открытый график → проданное время по
филиалам и мастерам. Новых коэффициентов, тарифов и правил найма раздел не
вводит.

### Определения

- **Открытый график и проданное время** — без изменений, определение
  «Загрузки мастеров» [обзора аналитики](analytics-overview.md#загрузка-мастеров):
  рабочие минуты — интервалы `staff_schedules` рабочих дней; проданное в
  графике — минуты клиентских записей (кроме `cancelled`, `no_show` и
  системных блокировок) внутри интервалов графика по ключу «мастер × филиал ×
  салонные сутки»; записи в сутки без графика — «вне графика», в процент не
  входят. Процент = проданное в графике / открытый график; без графика —
  `null`. Ручка использует ту же реализацию, поэтому её итог по всей
  организации совпадает с `occupancy` обзора за тот же период.
- **Физическая ёмкость** — уникальные физические места с проверенной
  вместимостью (рамки выше); CRM показывает число мест по справочнику
  `GET /v1/resources`. Часы физической ёмкости источником не определены:
  ответ отдаёт `physical_minutes = null` с причиной
  `physical_hours_source_missing`, а не ноль. Источник часов мест — отдельное
  решение.
- **Ориентир 70%** проданного времени от открытого графика — из обсуждения
  владельца 06.10.2026 (SUM-220 п. 30). CRM показывает его для сравнения;
  backend его не хранит и не применяет, автоматического запрета найма нет.

### Запрос и доступ

- `GET /v1/staff-capacity?days=7|30|90` (по умолчанию 30), сервисный токен и
  сессия CRM; другое `days` — 422.
- Альтернатива — обе даты `date_from` и `date_to`, включительно, максимум
  370 дней и не позже сегодняшнего дня платформы. Только одна дата или
  совместное указание `days` и дат — 422. Это продолжение backend
  `b71ea5fb53b04bc0a9986ee99eb14a704138e79b`, CRM
  `d30f9304b545c66b7f65e6e615cc37c2d1145843`; доставка отдельно.
- Период — последние `days` завершённых салонных дней, как у обзора.
- Доступ — раздел «Сотрудники»; область — филиалы сессии
  (`granted_location_ids`): владелец — вся организация, роль без
  подтверждённых филиалов — 403. Область применяется до суммирования: чужой
  филиал не попадает ни в строки, ни в итог.

### Ответ

| Поле | Смысл |
|---|---|
| `period` | `days`, `date_from`, `date_to`, `timezones` |
| `scope` | `organization` или `granted_branches` |
| `generated_at`, `freshness` | время ответа; свежесть синка графиков |
| `incomplete`, `incomplete_reasons` | причины обзора: `source_never_synced`, `source_stale`, `bookings_without_schedule`, `invalid_schedule_slots` |
| `totals` | минуты по всей области |
| `branches[]` | филиал: `location_id`, `name`, `masters` (мастера с графиком или записями в периоде), `physical_minutes` (`null`), `physical_unknown_reason` |
| `masters[]` | мастер × филиал: `staff_id`, `display_name`, `specialization`, `location_id`, `location_name` |

Общие поля `totals`, `branches[]` и `masters[]`: `status` (`ok` — есть
график, `no_schedule` — записи без графика, `empty` — ни графика, ни записей),
`work_minutes`, `booked_minutes`, `booked_in_schedule_minutes`,
`booked_without_schedule_minutes`, `free_in_schedule_minutes`, `percent`.
Свободные минуты считает backend из открытого графика и занятого внутри
него времени; без графика — `null`, не ноль. Это время, не количество
пустых окон и не свободная физическая ёмкость. В список филиалов входят
активные филиалы области и филиалы с данными за период. Разрез «по категории»
— специализация мастера из реестра, другой классификации нет.

### Граница

- Только чтение: записи, графики и YClients не меняются, схема БД и миграции
  не нужны.
- Загрузка не означает гарантию места (см. «Граница гарантии») и не влияет на
  начисления.
- Поставка (SHA, подключение роутера, Dev) — в
  [текущем состоянии](../docs/current-state.md) и [CHANGELOG](../CHANGELOG.md);
  этот раздел её не подтверждает.

## Остаток (не решено этим документом)

- Путь без `requestId` у `set_master_staff_day` остаётся только для старых
  вызовов: master-app его не использует. Сделать `requestId` обязательным
  (422 `request_id_required`) — следующий технический шаг вместе с
  обновлением тестов при подготовке production.
- 11 активных услуг без ресурса и четыре записи без ресурса требуют
  классификации данных (SUM-115 7-450, п. 2–3); до неё такие услуги не
  допускаются к подтверждённому графику.
- Бизнес-развилки нет; если владелец захочет строгую гарантию места, это
  новое решение (hold/условная запись в YClients), а не настройка этого
  контракта.
