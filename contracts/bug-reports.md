# Контракт: пользовательские баг-репорты

Решение голосового обсуждения 01.10.2026
([SUM-97](https://summy.youtrack.cloud/issue/SUM-97), вопрос 3, источник —
запись ответов обсуждения): форма баг-репорта нужна во всех пользовательских
приложениях — CRM для всех учётных записей, приложение клиента, приложение
мастера и публичный сайт. Образец — форма обращения мастера
`master-app/web/src/screens/ShiftIssue.tsx`. Почта и Telegram отложены;
внешние адреса и чат не назначены.

## Форма

- Поля: «Что случилось?» (обязательно, от 10 символов), шаги, чтобы
  повторить, и ожидаемый результат (оба необязательны).
- Сайт добавляет страницу, время и браузер в подготовленный текст; CRM и
  клиент с P24 передают только путь страницы, роль CRM добавляет сервер, тема
  обязательна (3–160). Приложение мастера передаёт тему, описание и фото.
  Имя, телефон и другие персональные данные форма сама не собирает.
- Подписанные поля, текстовые сообщения и `role="status"`/`role="alert"`,
  управление с клавиатуры (диалог CRM — Radix, сайт — нативный `<dialog>`).

## CRM, приложение клиента и приложение мастера — отдельная задача `[BUG]` в YouTrack

P24 (02.10.2026): [SUM-196](https://summy.youtrack.cloud/issue/SUM-196)
(основная, CRM и backend), клиентская часть —
[SUM-192](https://summy.youtrack.cloud/issue/SUM-192). Поручение 03.10.2026
([SUM-203](https://summy.youtrack.cloud/issue/SUM-203)): каждый отправленный
отчёт — **отдельная задача** проекта SUM в стадии «Очередь» с тегом «баг»;
приложение мастера переведено на тот же адаптер backend.

- **Исключение из учёта частями сводных.** Входящий баг-репорт — отдельная
  карточка, а не часть сводной ([доска](../ai/WORKFLOW.md#доска-youtrack));
  разные отчёты не объединяют в одну сводную. Префикс `[BUG]` в теме тегом не
  является.
- **Стадия и тег.** Задача создаётся с явным `Stage` = `Backlog` (на доске
  «Очередь», id значения `166-15`, настройка `YOUTRACK_BUG_STAGE_ID`) и затем
  доводится: пустая стадия ставится, отсутствующий тег «баг» (id `10-6`,
  `YOUTRACK_BUG_TAG_ID`) добавляется, состояние перечитывается. Уже заданную
  стадию сервер не меняет — задача, вручную продвинутая дальше, в «Очередь» не
  возвращается; массовой правки старых задач нет. Пока стадия и тег не
  подтверждены, ответ — 502 `issue_incomplete` с номером задачи и текстом
  «повтори»; успехом не считается. Повтор того же `requestId` доводит ту же
  задачу.
- **Тег «баг»** принадлежит `523uran523`, виден Summy Team; права применять его
  другим учётным записям не выдавались (03.10.2026). Если серверный токен
  принадлежит другой учётной записи, тег не встанет и отчёт честно останется
  `issue_incomplete` — нужен шаринг тега владельцем (решение о правах).

- **Путь.** CRM: диалог → `POST /api/app-bugs` (проверка origin по
  `ADMINAPP_PUBLIC_ORIGIN`, живая сессия любой роли, нужен
  `ADMINAPP_AUTH_PROVIDER=gateway`) → backend `POST /v1/app-bugs` с сервисным
  токеном и `X-Session-Token` (`require_live_crm_session`; master-сессии со
  `staff_id` не принимаются). Клиент: `/bug-report` только после входа → BFF
  `POST /client/api/app-bugs` (origin `CLIENT_PUBLIC_ORIGIN`, тело до 7,5 МБ) →
  backend `POST /v1/client/app-bugs` с `X-Client-Session-Token`
  (`required_account`, роль сотрудника не выдаётся). Мастер: `/app/bug/` →
  BFF `POST /v1/master/app-bugs` (origin, cookie сессии, поля и фото
  проверяются, multipart переводится в JSON) → backend
  `POST /v1/master/app-bugs` с сервисным токеном и `X-Master-Session-Token`
  (`resolve_master_scope`, живость мастера). Новых ACL и прав нет.
- **Поля и лимиты** (сервер проверяет, форма дублирует для удобства): тема
  3–160, описание 10–5000, шаги до 3000, ожидаемое до 2000; фото JPEG, PNG,
  WEBP или HEIC до 5 МБ с проверкой сигнатуры; `requestId` — UUID.
- **Контекст задачи** — только продукт (CRM, приложение клиента, приложение
  мастера), путь страницы без query и фрагмента,
  роль CRM (сервер, из сессии) и код отчёта. Имени, телефона, cookies,
  токенов, браузера и автоматических снимков нет; фото — только выбранное
  пользователем.
- **Ответ** `issueId` + `photoAttached`. Успех показывается только с номером
  задачи; «задача создана, фото не прикрепилось» — отдельное состояние, повтор
  с тем же `requestId` догружает фото в ту же задачу (если вложений у неё ещё
  нет). Текст и фото при ошибке остаются в форме.
- **Идемпотентность.** Код отчёта = хеш продукта, автора сессии и
  `requestId`, записан в описании задачи. Перед созданием — advisory-lock
  PostgreSQL по коду и поиск задачи с этим кодом в YouTrack; найденная задача
  возвращается вместо новой. Неизвестный исход создания (таймаут, 5xx) —
  502 `outcome_unknown`; повтор того же кода в течение 60 с получает 409
  `outcome_pending`, затем сверку поиском.
  **Ограничение:** окно 60 с и лимит 10 новых задач в час на автора хранятся в
  памяти процесса backend (не переживают рестарт, не делятся между
  воркерами); если индекс поиска YouTrack отстаёт дольше окна, дубль
  возможен. Миграций нет.
- **Настройки** (имена, не значения): только backend — `YOUTRACK_URL`,
  `YOUTRACK_TOKEN`, `YOUTRACK_PROJECT_ID`, `YOUTRACK_BUG_STAGE_ID`,
  `YOUTRACK_BUG_TAG_ID`. Токен только серверный, браузеру и BFF не выдаётся.
  Без `YOUTRACK_TOKEN` все три ручки отвечают 503 `youtrack_not_configured`, и
  форма честно пишет, что отчёт не отправлен. С 03.10.2026 23:05 на Dev у
  backend api задан `YOUTRACK_TOKEN` — тот же существующий ключ YouTrack
  (решение SUM-97 Q24-1); учётка владеет тегом «баг», шаринг не нужен;
  остальные `YOUTRACK_*` — значения по умолчанию кода. Значение хранится
  только на сервере вне Git. Реальный баг для проверки не создавался.
- Сайт по-прежнему вызывает локальную заглушку `submitBugReport`
  (`{ delivered: false, channel: "stub" }`) с кнопкой «Подготовить отчёт» и
  копированием текста; P24 его не меняет.

## Приложение мастера — обращение

С 03.10.2026 BFF мастера в YouTrack не ходит: `YOUTRACK_TOKEN`,
`YOUTRACK_PROJECT_ID` и чтение Связки ключей из прослойки сняты, отчёт
создаёт backend (раздел выше).

Форма обращения мастера сохраняет запись через
`POST /v1/master/shift/issues` (`master_requests`, категория `app_bug` — с
шагами и ожидаемым результатом, идемпотентный `request_id`). Вход «Сообщить
об ошибке» в профиле открывает ту же форму с категорией «Ошибка приложения»
(`/shift/problem/?category=app_bug`); вход «Сообщить о проблеме» и категория
«Рабочие вопросы» не изменились. Статус уведомления на почту показывает
backend (`email_status`), форма его не придумывает.

## Не путать с мониторингом синхронизации

Баг-репорт — сообщение человека. Автоматический сигнал о сбое синхронизации
YClients (T3, [SUM-185](https://summy.youtrack.cloud/issue/SUM-185)) — отдельная
функция с отдельным решением и задачей (SUM-97 T3, SUM-185); этот контракт
её канал не определяет, а баг-репорт не заменяет мониторинг. Канал сигнала
выбран отдельно 01.10.2026 — колокольчик владельца в CRM
([инфраструктура](../docs/infrastructure.md#синк-yclients-расписание-сигнал-и-повтор-sum-185-01102026)).
