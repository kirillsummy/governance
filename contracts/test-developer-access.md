# SUM-104 — разработчик на общем TEST

Контракт относится только к общему Docker Compose серверу TEST. У backend одна пара `TEST_DEVELOPER_LOGIN` / `TEST_DEVELOPER_PASSWORD` в закрытой конфигурации; BFF пароля не знают. Обычный вход всех трёх продуктов сохраняется. Пароль и токены не попадают в URL, клиентский bundle, Git и журналы.

## Включение и граница среды

После доставки изменения интерфейсов от 27.09.2026 обычные формы входа не показывают разработческий режим и ссылки на него. Для прямого перехода на TEST используются `/login_dev` в CRM (`https://201.51.9.79:8443/login_dev`), `/login_dev/` у мастера (`https://201.51.9.79:9443/login_dev/`) и `/client/login_dev` у клиента (`https://201.51.9.79/client/login_dev`). Старые прямые адреса мастера и клиента перенаправляются на новые. Знание адреса не даёт входа под учёткой: остаются серверные флаги TEST, логин и пароль разработчика и выбор существующей учётки. Общий HTTP Basic Auth стенда отключён с 30.09.2026 по SUM-152 ([инфраструктура](../docs/infrastructure.md)); единственное действие без входа разработчика — значок 🛠 копирования закрытого текста (раздел ниже). Три приложения развернуты на общем TEST 27.09.2026; точные SHA и границы проверки указаны в [текущем состоянии](../docs/history/current-state-log-2026-10-02.md#sum-104--отдельные-адреса-входа-на-test-27092026). Браузерный вход в рамках этой поставки по просьбе владельца не проверялся.

По умолчанию механизм выключен. Backend регистрирует `/v1/test-developer/*` только при `DEPLOYMENT_ENVIRONMENT=test` и `TEST_DEVELOPER_ENABLED=true`. Настройка требует stand facade YClients, отдельные PostgreSQL и MinIO, локальный SMS sink, выключенные Telegram/SMTP и платежный merchant, обязательную проверку CRM-сессий. Производственный backend с обычной конфигурацией не содержит маршрутов. Каждый BFF отдельно требует свой серверный флаг и `DEPLOYMENT_ENV=test` (у CRM `ADMINAPP_DEPLOYMENT_ENV`, у клиента `CLIENT_DEPLOYMENT_ENV`). Ни один из этих флагов не публикуется в браузер.

Перед включением оператор сверяет фактические env без вывода секретов, PostgreSQL endpoint и `alembic_version`, MinIO endpoint, compose overrides и работающие образы. Проверка только Git-ветки или VERSION недостаточна. Если внешнее направление не подтверждено как безопасное, механизм оставляют выключенным.

## Протокол

1. BFF передаёт логин и пароль серверному `/login`; backend ограничивает попытки и выдаёт случайный токен разработчика на 30 минут. BFF держит его в `HttpOnly` cookie. Продуктовая сессия ещё не выдаётся.
2. `/profiles` показывает существующие учётки. CRM фильтрует активный допуск по роли, но при выборе роль заново читает из backend. Мастер выбирается только по активной однозначной привязке `staff_user`. Клиент выбирается из действующего профиля текущей организации без административной роли.
3. `/select` заново проверяет учётку и выдаёт продуктовую сессию, связанную с поколением сессии разработчика. Продуктовые запросы продолжают обычные проверки допуска, филиала, сотрудника, клиента и срока. Следующий выбор увеличивает поколение и гасит предыдущую сессию.
4. `/logout` отзывает сессию разработчика и удаляет cookie продукта. Обычный вход работает самостоятельно.

Backend хранит события `login/select/logout` и журнал изменяющих запросов с фактом тестового входа, выбранной учёткой, методом, путём, request ID и кодом ответа, когда он доступен; CRM BFF фиксирует попытку до выполнения запроса. Общий пароль не устанавливает конкретного человека.

## Профили рабочих мест CRM (30.09.2026)

После входа разработчика `/login_dev` CRM кроме трёх ролей существующих учёток (владелец, управляющий, администратор) предлагает три рабочих места: «Кладовщик», «Менеджер по закупкам», «Бухгалтер». Это синтетические допуски `test-storekeeper`, `test-purchaser`, `test-accountant`, которые создаёт `backend/scripts/seed_test_workplace_profiles.py` только на общем TEST. Протокол прежний: `/select` заново читает допуск и роль из backend, сессия связана с поколением сессии разработчика, изменяющие запросы попадают в журнал действий. Дверь CRM выдаёт cookie ролей `storekeeper`, `purchaser` и `accountant` только этим трём идентификаторам; учётки реальных людей с ролью бухгалтера через `/login_dev` не выбираются. Роли, разрешённые действия и остаток — в [контракте рабочих мест](role-workplaces.md).

По SUM-165 в `crm/test` добавлено четвёртое рабочее место «Курьер» — синтетический допуск `test-courier` с ролью `courier`, который создаёт тот же скрипт после ревизии `0159_courier_deliveries`. Правило прежнее: cookie роли `courier` дверь CRM выдаёт только этому идентификатору, `/select` заново читает допуск из backend. Логин и пароль разработчика, срок токена, поколения сессий и журнал действий не менялись. На общем TEST развёрнуто 30.09.2026, профиль `test-courier` создан; вход под ним не выполнялся.

## Компактный вход CRM и копирование закрытого текста (03.10.2026)

Поручение пользователя 03.10.2026. После входа разработчика `/login_dev` CRM
показывает один столбик из семи одинаковых кнопок полной ширины: «Владелец»,
«Управляющий», «Администратор» (выбор существующей учётки раскрывается под
кнопкой роли) и «Кладовщик», «Менеджер по закупкам», «Бухгалтер», «Курьер»
(прямой выбор синтетического профиля; недоступный профиль — неактивная
кнопка). Роли, профили, маршруты, проверки двери и выход прежние.

Во всех трёх существующих входах разработчика (CRM `/login_dev`, мастер
`/login_dev/`, клиент `/client/login_dev`) в строке заголовка формы логина и
пароля, слева от «Тестовый вход разработчика», — небольшая неброская
кнопка-значок 🛠 без видимой подписи, рамки и поля (`type=button`, форму не
отправляет, доступное имя «Ключ» только как `aria-label`; после нажатия
рядом — маленькая отметка ✓/✕). По уточнениям
пользователя 03.10.2026 она доступна до входа разработчика; после входа на
экране ролей и профилей её нет, прежнее поле со стрелкой «Скопировать» убрано.
Кнопка копирует в буфер обмена закрытый текст — отдельное значение, не пароль
разработчика:

- значение — закрытая настройка backend `TEST_DEVELOPER_COPY_TEXT`; backend не
  стартует, если она задана без `TEST_DEVELOPER_ENABLED`; задаётся только в
  непубличном runtime общего Dev, на Prod её нет;
- `GET /v1/test-developer/available` отдаёт признак `copy_available` без
  значения; `POST /v1/test-developer/copy` требует только сервисный токен
  (токен разработчика не нужен), отвечает текстом с `Cache-Control: no-store`,
  без настройки — 503; маршруты `/v1/test-developer/*` регистрируются только
  на изолированном TEST, на Prod их нет;
- BFF CRM (`/api/auth/test-developer/copy`), мастера
  (`/auth/test-developer/copy`) и клиента (`/client/api/test-developer/copy`)
  проксируют copy без cookie разработчика, сохраняя серверные флаги TEST,
  доступность изолированного стенда, проверку origin и `no-store`;
  `/profiles`, `/select` и `/logout` по-прежнему требуют действующий токен
  разработчика;
- браузер получает текст только в ответ на нажатие и сразу кладёт его в буфер
  обмена (Clipboard API), текст не показывается и не хранится в DOM или
  storage; в Git, журналах, `VITE_*`/`NEXT_PUBLIC_*` и сборках его нет.

## Изоляция и откат

### SUM-175: открыть смену без QR на локальном и TEST

`GET /v1/master/auth/session` отдаёт `test_shift_open_enabled`. В локальной
среде с локальными PostgreSQL и MinIO без TLS либо на изолированном TEST с
`TEST_DEVELOPER_ENABLED=true` значение равно `true`; приложение мастера
открывает смену кнопкой через `POST /v1/master/shift/open-test` без сканирования.
Маршрут требует действующую master-сессию и сервисный токен. Он создаёт обычную
карточку процесса в первом действующем филиале мастера с отметкой «Тестовое
место», без записи в справочнике мест и без свидетельства о состоянии места.
Если действующего филиала нет, команда отвечает отказом. В production маршрут
не регистрируется, признак ложен, кнопка ведёт к прежнему QR-сценарию. Тестовые
карточки остаются в истории локальной или TEST базы после выключения режима.

Тестовые записи остаются в TEST-БД и TEST-MinIO. YClients API работает через stand facade без исходящих записей; SMS идёт в локальный sink; Telegram и SMTP выключены; платёжный merchant отсутствует. Для иных исходящих каналов требуется отдельное подтверждение или отказ действия до включения. Дамп TEST содержит реальные данные, поэтому даже без внешней отправки доступ к нему ограничен.

Для выключения сначала снять BFF-флаги, затем `TEST_DEVELOPER_ENABLED`; отзыв сессий происходит по backend и без этого флага токены больше не принимаются. Данные и аудит при откате кода сохраняются; миграцию 0143 не откатывать после создания событий без отдельного плана сохранения данных. Следующие релизы ветки `test` обязаны проверять этот контракт на backend, трёх BFF и в браузере. Ветвление само по себе не гарантирует, что код никогда не попадёт в production: защита должна оставаться в startup guard, маршрутах и релизной проверке.

## SUM-150: демо-учётка клиента и роли CRM

С 30.09.2026 выбор ролей CRM `/login_dev` — ровно «Владелец», «Управляющий», «Администратор»; BFF отклоняет `/profiles` с другой ролью и не выдаёт cookie учётке другой роли, кроме синтетических рабочих мест выше. Клиентский BFF переводит недоступность backend в 503 и показывает причину по коду ответа, не раскрывая, что именно неверно при 401.

На общем TEST есть одна синтетическая клиентская учётка «ТЕСТ Демо-клиент» (телефон `+7 000 000-00-01`, несуществующий), которую создаёт `backend/scripts/seed_test_client_demo.py` только при `DEPLOYMENT_ENVIRONMENT=test`, включённом входе разработчика и локальной PostgreSQL стенда. Состав: профиль, 5 записей на существующие услугу, студию и мастера (3 завершённые с оплатой визита, 2 предстоящие), рекламация с начислением 500, карта `TEST-DEMO-0001` с балансом 1 500 и начисление 1 000. Повторный запуск не создаёт дублей и переносит прошедшие незавершённые демо-записи на будущие даты. На стенде баланс клиента читается из зеркала `client_loyalty_cards`. Отключение без удаления истории — `deleted_at` у карточки клиента и её записей. Первый запуск — 01.10.2026, exit 0.
