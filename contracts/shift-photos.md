# Контракт: снимки рабочего места на смене

**От:** архитектор · **Дата:** 26.08.2026 · **Статус:** принят, к постройке
**Основание:** слово владельца 26.08.2026 сессии «смена — визуальные экраны»:
«мастер фотографирует рабочее место когда сдаёт, и админ тоже»; «прикрепить
только через снимок непосредственно с камеры»; «корректно организовано
хранение в нашем хранилище»; «по хранению фото нужна обязательная привязка
к сотруднику»; «техническая возможность добавить фото из приложения мастера
при его проверке и с мобильной версии CRM для админов».

Стык межпродуктовый: кадры ПИШУТ два продукта (приложение мастера и CRM),
ЧИТАЕТ третий вид экрана — сверка у управляющего. Поэтому правила здесь,
а не в памятке одного продукта.

## Решение: медиатека + связь с карточкой (вариант А)

Снимок — полноценный житель медиатеки, карточка смены знает о нём через
отдельную связь. Никаких вторых мест хранения.

```
media_assets            файл: bucket/key, mime, размеры, checksum, captured_at
  └─ content_items      смысл: purpose='shift_check', видимость
       ├─ media_library_items   владелец: owner_type='staff', owner_id
       └─ process_photos        СВЯЗЬ с картой смены (НОВАЯ таблица)
```

`process_photos`: `process_id → processes`, `content_item_id → content_items`
(UNIQUE — один кадр живёт на одной карточке), `side` CHECK `('master','admin')`,
`created_at`; индекс по `process_id`.

Почему не `process_attachments` (варианты Б/В, отвергнуты): у вложений свой
`storage_key` вне медиатеки — расширять их значило бы дать файлу два дома
и врасти в легаси-путь, который после 1.0 сам поедет на медиатеку; а без
медиатеки нет ни владельца-сотрудника (там только `uploaded_by_name`
строкой), ни производных, ни правил хранения. Новую вещь строим на новой
системе.

## Инварианты

1. **`purpose = 'shift_check'`** — новый код в закрытом списке
   `content_items.purpose` (CHECK; расширение — аддитивная миграция).
   Один purpose на обе стороны: чей кадр — говорит `side` СВЯЗИ, а не
   назначение контента. Не путать с `resource_photo` — то витринное фото
   места как справочного объекта, здесь операционный кадр состояния.
2. **Сторона обязательна:** `side='master'` — кадры мастера при сдаче,
   `side='admin'` — кадры администратора при проверке. Два независимых
   комплекта, как и отметки сторон (слово владельца). Сверка парами — чтение
   `process_photos` по карточке с группировкой по `side`.
3. **Привязка к сотруднику обязательна** (слово владельца 26.08):
   `media_library_items(owner_type='staff', owner_id=<АВТОР кадра>)`.
   Прочтение архитектора: владелец кадра в медиатеке — тот, кто снял
   (у мастерского кадра — мастер, у админского — администратор); мастер
   смены и так доступен через карточку, дублировать его во владельца
   админского кадра не нужно. ⚠️ Прочтение сверить с владельцем при показе
   экранов; правка дешёвая (UPDATE одного поля), стройку не блокирует.
4. **Хранение** — по правилам медиатеки: оригинал в
   `originals/<owner_type>/<owner_id>/…` рабочего бакета `summy-media`,
   производные по профилям (превью для карточки — из конфига профилей,
   не изобретать размеры на месте). `s3_endpoint` обязателен в prod.
5. **«Только с камеры» — граница честности UI, не сервера.** Оба клиента
   открывают именно камеру (capture), без выбора из галереи. Сервер
   принимает файл от авторизованного актора и подделку EXIF не разоблачает —
   это осознанная граница v1, а не забытый случай. `captured_at` пишем,
   когда клиент его отдал.
6. **Кадры не удаляются.** Снимок сверки — свидетельство: «прикрепили и
   тихо убрали» — та же болезнь, что со штрафом. Пере-снял — новый кадр
   рядом; снятие с показа, если понадобится, — пометкой новой колонкой,
   не удалением строк и файлов (в v1 не строим).
7. **Ручки пишущих сторон симметричны по правам:** мастер добавляет кадр
   своей смены со своей стороны, администратор — со стороны `admin`
   (мобильная CRM). Актор обязателен (`X-Actor-*`), идемпотентность — по
   принятому в продукте способу (уникальный ключ нажатия). Форму ручек
   проектирует ревизия платформы в границах этого контракта.

   *Форма, выбранная ревизией (backend#47, зафиксировано 26.08.2026):*
   мастерская ручка `POST /v1/master/shift/photos` НЕ принимает номер
   карточки — сдаваемую смену находит платформа по самому актору-мастеру.
   Это серверная гарантия «кадр только в свою сверку» вместо клиентского
   обещания. Асимметрия с админской стороной намеренна: у мастера контекст
   «моя смена», у админа — «эта карточка»; симметрия контракта — по правам,
   не по форме. Обязательное следствие с тестом: у мастера бывают ДВЕ
   карточки за день (утренняя закрытая + вторая после пересадки, см.
   backend#46) — резолв обязан класть кадр в СДАВАЕМУЮ, не в закрытую.

## Чего контракт сознательно НЕ покрывает

- Сроки этапов смены — живут в машине процесса и метле `sweep_stale_shifts`
  (конец суток, подтверждено владельцем 26.08); кадры на сроки не влияют.
- Обязательность кадра для перехода этапа (можно ли сдать смену без фото) —
  вопрос машине процесса, решается владельцем отдельно; v1 кадры не
  блокируют переходы, пока владелец не сказал иного.
- Фотоотчёты уборки как отдельный процесс и прочие фото-стадии — та же
  цепочка медиатеки, но свой заход со своим словом владельца.
- Число кадров на сторону не ограничиваем в v1; если владелец захочет
  лимит — CHECK/валидация отдельной правкой.

## Порядок стройки

Визуальный этап экранов может идти на стендовой оснастке до ревизии (задание
смены, порядок владельца «сначала визуал»). Ревизия платформы — аддитивная,
от `dev`, обычным конвейером; требования хранения владелец дал явно 26.08,
так что хранилищный кусок его словом разблокирован — очерёдность визуала и
ревизии сессия решает с владельцем сама.
