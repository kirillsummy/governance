# Запись клиента мастером

Решение владельца от 23.09.2026: единая форма записи существующего или нового
клиента доступна в основном сценарии приложения мастера отдельно от тестовой
оплаты. Повтор завершённого заказа должен создавать новую запись, не меняя
исходный заказ. Статус: обычная запись реализована в `master-app/work`
(`1f65ffa05bf7e7c42776664f33c372741951eee0`) и `backend/work`
(`fb5c819e5077dfc123ced3501d50deaead84218e`,
`e80da79993ff8782fc7a003258501d0423ec0863`); повтор реализован в
тестовом orders-контуре и ожидает задачи №2. Выкладка на TEST, приёмка через
настоящий интерфейс с YClients и production-включение не подтверждены.

Источник правил и границ: задача №1–2 в
`master-app/docs/master-app-v1-backlog-2026-09-23.md`, проект контракта
`backend/docs/master-booking-contract-draft-2026-09-23.md` и
[тестовый контракт заказов](orders-payments-test.md). Здесь находятся целевые
правила записи мастером; правила денег остаются в тестовом контракте и
[денежном DoD](money-dod.md).

## Область и граница включения

- Мастер из действующей серверной сессии находит существующего клиента или
  создаёт локальную карточку по имени и телефону, выбирает доступную услугу,
  разрешённую точку, дату и свободный слот и записывает клиента только к себе.
  Клиентское приложение, аккаунт клиента, карта и согласие на их использование
  для этой команды не требуются.
- Основной вход не зависит от `VITE_ORDERS_TEST_ENABLED`. На backend отдельный
  `MASTER_BOOKING_ENABLED` выключен по умолчанию и открывает только booking API;
  `ORDERS_TEST_ENABLED` им не включается. Требуется настроенный секрет очереди.
- Оплата, платёжная ссылка, QR, возвраты, отмена, завершение заказа и
  административные orders-команды остаются в тестовом контуре. Наличие формы
  записи не делает sandbox-оплату production-способом оплаты.
- Повтор описан ниже как целевой сценарий задачи №2. Текущая тестовая
  реализация не означает, что повтор уже включён в основной интерфейс.

## Доступ и поверхность API

- Браузер обращается к backend только через same-origin BFF с точным
  master allowlist. Сервисный токен и master-сессионный токен не попадают в
  браузерный bundle. Административные пути этим сценарием не открываются.
- Для обычной записи доступны `GET /v1/master/orders/catalog`,
  `GET /v1/master/orders/clients`, `GET /v1/master/orders/slots`,
  `POST /v1/master/clients` для нового клиента, `POST /v1/master/orders` и
  `GET /v1/master/orders/{order_id}/booking-status`.
- Backend устанавливает `staff_id` из master-сессии. Переданный `masterId`
  обязан совпасть с ним; права на клиента, услугу, точку, слот, заказ и статус
  проверяются сервером в пределах организации. Чужой заказ или статус не
  раскрывается, включая подтверждение его существования.
- Поиск существующего клиента возвращает безопасное публичное имя и состояние
  связи `mine` / `unassigned` / `other_master`, без телефона, ID другого мастера
  и чужих визитов. Совпавший нормализованный телефон не создаёт дубль;
  неоднозначное совпадение требует явного выбора.

## Создание и подтверждение

- Слоты берутся из общего backend/YClients механизма. Подписанный слот и
  доступность повторно проверяются перед внешней командой; локальный резерв
  защищает от конкурирующего бронирования. Занятый или устаревший слот даёт
  понятный конфликт и возможность выбрать другой.
- `requestId` — ключ идемпотентности. Тот же состав с тем же ключом возвращает
  тот же результат; другой состав с тем же ключом отвергается. После таймаута
  или неизвестного ответа повторяется только тот же запрос с исходным ключом
  для восстановления результата; новый POST с новым ключом запрещён. Внешний
  результат сверяется с YClients по устойчивому идентификатору. Имя клиента и
  время не являются ключом.
- `POST` отвечает `202` о принятии команды в очередь, а не об успешной записи
  в YClients. Узкий статус возвращает `queued`, `dispatching`, `unknown`,
  `confirmed` или `rejected`. UI объявляет подтверждение только после
  `confirmed`; неизвестный результат и отказ не изображаются успехом.
- После подтверждения штатный синк связывает внешний record с одной записью
  `appointments`; она появляется в «Сегодня», карточке визита и занятости
  «Расписания». Синк асинхронный: сообщение о подтверждении не обещает
  мгновенного появления карточки. Перезагрузка должна сохранять результат.

## Целостность заказа и зеркала

- Один внешний record соответствует одной канонической записи и одному
  каноническому заказу `S-*`, созданному этим сценарием. Импорт не создаёт для
  того же `appointment_id` дополнительный заказ `V-*`.
- Штатный импорт публикует `appointments` и `external_refs` одной транзакцией.
  Локальный интеграционный тест проверил связь `S-*` с зеркалом без `V-*`,
  чтение записи в дне и занятости в календаре. Это не заменяет проверку
  настоящего импортёра и YClients после выкладки на TEST.
- Если ранее созданный `V-*` уже имеет тот же внешний record и позднее
  обнаруживается связь с `S-*`, историю, платежи, начисления, аудит и ссылки
  на старый ID нельзя автоматически удалить или переназначить. Этот
  пограничный порядок пока не доказан для штатного импорта; его диагностируют
  отдельно. Правило миграции или исторического псевдонима утверждается только
  при подтверждённой необходимости и оценке зависимостей.

## Повтор завершённого заказа — целевой сценарий задачи №2

- Повтор доступен только мастеру собственного завершённого заказа. Чужой или
  незавершённый заказ повторить нельзя. Исходный заказ, его время, номер,
  статусы и история не изменяются: создаётся новый заказ с новым ID.
- Backend восстанавливает из исходного заказа клиента, одну однозначную
  услугу, студию и текущего мастера. Экран выбирает только будущую дату и
  свежий слот, привязанный к ID исходного заказа. Неоднозначный состав или
  изменившаяся студия не угадываются — мастер переходит к обычной форме.
- `GET /v1/master/orders/{order_id}/repeat-slots` и
  `POST /v1/master/orders/{order_id}/repeat` становятся частью основной
  master-поверхности только при реализации задачи №2 с прежней проверкой
  прав и точным BFF allowlist. Слот другого заказа и занятый слот отвергаются.
- Повтор идемпотентен по `requestId`: двойной тап создаёт одну новую запись.
  После неизвестного ответа UI повторяет только ту же команду с тем же
  ключом для восстановления результата. Повтор не создаёт и не меняет постоянную
  [связь клиента с мастером](master-client-ownership.md).

## Приёмка и включение

После выкладки точных коммитов backend и master-app на TEST проверить через
настоящий интерфейс в изолированной компании YClients:

1. Запись существующего и нового клиента без тестового флага и карты;
   отсутствие дубля телефона, отказ для чужого мастера/клиента, конфликт слота
   и идемпотентность.
2. Подтверждение внешней записи и синк: одна карточка в «Сегодня», корректная
   услуга, занятость в «Расписании», тот же результат после перезагрузки и
   отсутствие второго заказа для одного внешнего record.
3. Точный BFF allowlist и отсутствие оплаты, отмены и административных команд
   в основном booking-пути. Зафиксировать SHA, тестовую компанию и результат
   синка без персональных данных клиентов и секретов.
4. После реализации задачи №2 отдельно проверить права на повтор, свежие
   слоты, двойной тап, timeout, неизменность исходного заказа и отсутствие
   дубля в зеркале.

Текущий локальный stand блокирует исходящие команды YClients; демонстрационный
API и локальная PostgreSQL-проверка не являются внешней приёмкой. Этот контракт
сам по себе не разрешает deployment, production-включение или реальные платежи.
