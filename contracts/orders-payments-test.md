# Запись, заказ и оплата: тестовый контур

Решение владельца от 17.09.2026. Статус: реализация и ревью; включение в production
не разрешено. Уточняет `money-dod.md`, не заменяет канонический расчёт `earnings`.

Основная запись клиента мастером теперь описана в отдельном
[booking-контракте](master-booking.md). Здесь сохраняются тестовые правила
оплаты, QR, возвратов, отмены, закрытия и остальных orders-действий; строки
ниже о записи и повторе отражают исходный feature-контур и не включают эти
действия в production. Повтор выведен в основной сценарий в `work` по
[booking-контракту](master-booking.md); TEST-приёмка и production-включение
не подтверждены.

> Уточнение после объединения DOC: документ описывает реализованный feature-поток
> ссылок/QR. Последующее требование владельца — привязка карты в клиентском приложении;
> её реализация не подтверждена. Сохранённый контракт не объявляет старый UX итоговой целью.
> [Состояние](../docs/current-state.md).

## Инварианты

- Один заказ связан с записью, клиентом, студией, мастером и позициями услуг.
  Номер неизменен при переносе и повторной выдаче ссылки. Имена и время не ключи.
- Календарь общий. Все входы используют backend и один адаптер YClients;
  локальная бронь резервирует интервал до подтверждения внешней команды.
  Неизвестный результат требует сверки, а не повторной записи.
- Клиент видит свои заказы; мастер — свои записи. Администратор, управляющий
  и владелец выполняют административные действия под проверенной CRM-сессией.
  Запрос отмены не отменяет запись. Отмена требует причины и сохраняет историю.
- Оказание услуги, оплата и выплата мастеру имеют независимые состояния.
  Завершение услуги фиксирует состав и итоговую сумму. После выдачи ссылки
  сумма неизменна; исправление проводится явно, с аудитом.
- Яндекс Пэй/Сплит работает только через sandbox. Суммы — Decimal RUB,
  идентификаторы заказа и операции проверяются на сервере. Переход браузера
  по success URL не является оплатой. Подтверждение — проверенный API провайдера.
- Создание платежа и возврат имеют устойчивые ключи идемпотентности.
  После таймаута сначала сверка. Повтор вебхука не создаёт финансовый эффект.
- Начисление использует существующие фиксированные ставки `pricing` и
  существующий источник `payroll_closings` / `earnings`; второго журнала нет.
  Для нового потока начисление доступно после оказания и подтверждения оплаты.
  Возврат клиенту не определяет автоматически удержание с мастера: это отдельная
  корректировка с основанием в существующем финансовом контуре. До её сверки
  заказ отмечается как требующий финансовой проверки.
- Чек показывается только после подтверждения кассой. Платёжная квитанция,
  перенаправление и номер заказа не выдаются за фискальный чек.
- Подтверждения и напоминания имеют очередь и ключ дедупликации. На тесте
  адресат — тестовый приёмник; сообщения настоящим клиентам не отправляются.

## Повторная запись завершённого заказа

Реализовано в `master-app/work` (`ca1e548`) и `backend/work` (`8e749a8`).
Это feature-код тестового контура, а не подтверждение production-включения.
Целевые права, состав, идемпотентность и инвариант неизменности исходного
заказа закреплены в [booking-контракте](master-booking.md). Этот раздел
сохраняет происхождение тестовой реализации, не дублируя целевые правила.

## Изменения прежних решений

Сайт теперь направляет кнопки записи в `/client/book` с контекстом выбранной
услуги, студии или мастера. Требование 17.09 «без кнопки на сайте» заменено
новым явным требованием владельца. Личный кабинет остаётся отдельным продуктом.
Устаревшее правило сайта «только виджет YClients» заменено общей записью через
backend; интеграция с YClients сохраняется в backend.

## Приёмка

Создание из всех трёх источников, конкурирующая бронь, перенос, запрос и решение
отмены, услуга, сумма, повторная ссылка, sandbox CAPTURED, повтор события,
потерянный ответ, частичный/полный возврат, отсутствие чужих заказов, начисление
ровно один раз, сверка выплат, напоминания и недоступность провайдера.
Реальные деньги и закрытые периоды не проверяются в этой задаче: согласно
`money-dod.md` зелёный тестовый прогон не означает production-ready.

## Соответствие плану владельца

| Требование | Реализация и граница проверки |
|---|---|
| Общий календарь CRM, сайта и мастеров | Общий backend, локальный резерв интервалов, источник свободного времени YClients; отдельный экран календаря CRM. Внешний тестовый филиал ещё не подключён. |
| Карточка заказа | Неизменяемый номер, клиент, мастер, услуги, время, итог; независимые состояния услуги и оплаты. |
| Создание, перенос, отмена | Клиент, мастер и CRM создают через общий резерв; перенос и отмена доступны администратору с причиной. Запрос клиента/мастера не отменяет запись. |
| История изменений | Append-only события, версии заказа, устойчивые команды; после неизвестного ответа сверка без повторной записи. |
| Защита от двойной записи | Общая блокировка календаря и проверка пересечения интервалов; на стороне YClients запрет записи в занятое время. Живая конкурентная приёмка выделенного филиала остаётся обязательной. |
| Авторизация и CRM-клиент | Клиентская сессия после OTP, связь по подтверждённому телефону; собственные заказы. Мастер связан через staff_user, CRM через проверенную gateway-сессию. SMS-адаптер наследуется из клиентского контура, внешний провайдер не подключён. |
| Оказание, сумма, качество | Начало → существующий контроль качества → завершение с итогом по позициям. Работа и материалы подтверждаются раздельными фото; отказ от гарантии их не заменяет. Закрытие и начисление разделены по [контракту фотоподтверждений](appointment-closure-photos.md). |
| Платёжная ссылка и QR | Один sandbox-платёж на номер заказа, замороженная сумма; повторная выдача той же ссылки. QR формируется локально в приложении мастера. |
| Яндекс Пэй/Сплит, подтверждение | Sandbox-адаптер CARD/SPLIT, подписанный webhook, чтение состояния у провайдера; повторы не создают повторное начисление. Merchant ID не предоставлен, внешний цикл не проверен. |
| Возвраты | Причина, идемпотентная команда, сверка внешней операции и остатка; частичные и полные состояния. На тесте targetCart распределяет возврат по порядку позиций; финансовая политика требует отдельной приёмки. |
| Начисления и выплаты | Существующий фиксированный pricing/payroll/earnings, начисление один раз после оплаты и качества. Карточка читает существующие выплаты, CRM ведёт в штатный раздел баланса. Автоматическая банковская выплата не добавлялась. |
| Сверка | Статусы, операции провайдера, история, команды с неизвестным результатом; возврат помечает заказ для финансовой сверки без скрытого удержания мастеру. |
| Статусы во всех приложениях | Общие проекции backend; обновление открытых карточек и календаря каждые 5 секунд. Возврат браузера с оплаты не подтверждает деньги. |
| Подтверждения и напоминания | Очередь с дедупликацией и отменой старых напоминаний при переносе; тестовый приёмник в БД. Доставка настоящим клиентам выключена. |
| Клиентское приложение | Запись, детали и номер, запрос отмены, история, итог, переход к оплате и результат. Предыдущая реализация OTP/CRM-связи сохранена. |
| Фискальный чек | UI честно показывает отсутствие чека. Адаптер кассы НЕ реализован: касса пока не выбрана. Оплата и чек не отождествляются. |
| Кнопки сайта | Переход в `/client/book?source=website` с категорией услуги, студией или мастером. Флаг по умолчанию выключен. |

Общий статус: код для тестового ревью, не готовность всего денежного контура.
Нужны выбор кассы и её адаптер, sandbox merchant ID, выделенный филиал YClients,
настройка SMS/уведомлений и живой сквозной прогон на тестовых реквизитах.
