# Контракт: видимость клиентов для мастера

Статус: целевое правило v1 по задаче №15 исполняемого backlog. Минимальный
список реализован в `backend/work` (`7c87060`); история из сегодняшней записи
ещё не реализована. Существующая шторка записи даёт часть данных, но не
выполняет все описанные здесь ограничения. TEST-приёмка и production-включение
этим документом не утверждаются.

Источник: [решение владельца от 23.09.2026, п. 13](https://github.com/kirillsummy/master-app/blob/21348358f2db2450865ce3e05f5a0d9851847a71/docs/master-app-v1/owner-decisions-2026-09-23.md)
и подтверждение владельца от 25.09.2026: фото материалов прошлых визитов
доступны только из карточки собственной сегодняшней записи клиента, в том числе
для работ коллег. Backend владеет проверкой прав, связью записей и проекциями;
master-app обращается к нему через BFF. Этот контракт не меняет
[постоянную связь](master-client-ownership.md) и её финансовый смысл.

## Две области доступа

| Область | Основание доступа | Содержимое |
|---|---|---|
| Список обслуженных клиентов | Мастер хотя бы раз обслужил клиента в своей организации; подтверждённая backend связь с записью | Минимальная карточка клиента и состояние постоянной связи относительно мастера |
| История для подготовки к визиту | Собственная запись мастера на текущую бизнес-дату платформы, связанная с этим клиентом | Предыдущие услуги и работы клиента, включая работы коллег, в пределах полей ниже |

Наличие клиента в списке, его поиск и состояние `mine` не открывают историю.
Ownership не является критерием включения в список: обслуженный клиент виден
и при `unassigned` или `other_master`. Чтение ни в одной области не создаёт
и не меняет ownership, приглашение или запись.

Backend проверяет организацию, действующую сессию мастера и основание доступа
при каждом запросе, включая выдачу каждого файла. Для новых проекций BFF
должен пропускать только согласованные master-scoped пути; общие `/v1/clients`,
аналитические и административные маршруты не становятся доступными браузеру
мастера. Текущий BFF пропускает префикс `/v1/master/` целиком, поэтому
изоляцию новых путей нельзя считать уже обеспеченной одним allowlist.
Существующие `client-network`, `client-work-photos` и `client-notes` в
`backend/work` открываются по принадлежности записи мастеру без проверки её
текущей бизнес-даты. При реализации истории эти пути нужно привести к новой
границе доступа или исключить из BFF; добавление новой ручки само по себе не
закрывает старый путь.

## Минимальный список v1

Целевая отдельная поверхность — `GET /v1/master/clients?query&limit&cursor`.
Ответ содержит строки `{ id, display_name, ownership_state }` и непрозрачный
`next_cursor` либо `null`. `ownership_state` принимает `mine`, `unassigned`,
`other_master` и вычисляется backend по действующей связи. Идентификатор
другого мастера не выдаётся. Список содержит только клиентов с достоверным
фактом обслуживания данным мастером; клиент, которого он только создал для
будущей записи или нашёл при поиске для записи, не добавляется автоматически.

Для реализации списка в `backend/work` фактом состоявшегося визита считаются
записи в состояниях `arrived` и `completed`, как в материализации visits.
Состояния `planned` и `no_show` не включают клиента в список. Выборка по
связи записи не размножает клиента при нескольких визитах; курсор идёт по
уникальному идентификатору клиента.

Поиск выполняется backend **внутри разрешённого набора**. Пустой результат
одинаков для отсутствующего и недоступного клиента: поиск не служит проверкой
существования чужой карточки. Пагинация имеет стабильный порядок и курсор,
не пропускает и не повторяет строки при последовательном чтении страниц.
Точный способ нормализации поисковой строки и формат курсора остаются
внутренними для backend; frontend не загружает всю базу для локального поиска.

В DTO списка отсутствуют телефон, email, адрес, дата рождения, аватар автора
отзыва, контакты, платежи, заметки, фото и история визитов. Уровень и
регулярность не подставляются по догадке: определения этих признаков ещё не
утверждены владельцем, поэтому в v1 они не выдаются.

## История из сегодняшней записи

Целевая отдельная поверхность —
`GET /v1/master/appointments/{appointment_id}/client-history`. Backend
проверяет, что запись принадлежит текущему мастеру и приходится на текущую
бизнес-дату платформы (`Europe/Moscow`), затем берёт её связанного клиента.
Произвольный `client_id` в запросе не принимается. Чужая запись, запись на
другую дату и клиент без достоверной связи с записью не расширяют доступ.
Право проверяется заново при каждом запросе; вчерашний доступ не сохраняется.

Ответ содержит только предыдущие визиты этого клиента в разрешённой области
организации: дату и время, услуги и их состав, тайминг, фото результата `work`
и фото материалов `materials`. Исторические работы коллег допустимы, но имя и
идентификатор коллеги не выдаются до отдельного решения владельца. Фото
материалов — служебные: они доступны только через эту проекцию и защищённую
выдачу файла в том же контексте записи. Они не попадают в общий список,
обычную историю работ, портфолио или публичные API. Недоступный или
отсутствующий файл не заменяется вымышленным изображением.

Мастер может видеть только **свои** отзывы через существующий
`GET /v1/profile/reviews`. Связь отзыва с клиентом/визитом можно показывать
лишь при достоверной backend-связи с записью; совпадение имени автора, даты
или текста не доказывает её. Оценки и отзывы других мастеров в эту проекцию
не входят. Телефоны, email, иные контакты, платежи и начисления не выдаются
ни в ответе истории, ни в ссылках на её медиа.

## Отложено и приёмка

Приглашённые клиенты должны получить отдельный статус в будущем списке, но
механика приглашения и подтверждения клиентом не утверждена окончательно.
Она не входит в v1 и не создаёт ownership. Предпочтения и наблюдения мастера,
уровень, регулярность, поиск необслуженного клиента вне сценария записи и
показ имени коллеги требуют отдельных решений. Этот контракт не отменяет
существующий узкий сценарий ввода телефона для создания записи; его права
нужно проверять по [контракту записи](master-booking.md).

При реализации отдельно проверить: обслуженный клиент виден без ownership;
чужой необслуженный не обнаруживается поиском; страницы не дублируются;
история и оба вида фото доступны только через свою сегодняшнюю запись;
прошедшая или чужая запись не даёт доступа; отзывы другого мастера, контакты
и платежи отсутствуют в DTO, DOM и логах. Публикация контракта не означает
прохождение этих проверок.
