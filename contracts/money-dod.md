# Контракт: готовность денежного контура (Definition of Done)

Деньги считает только бэкенд; фронты показывают. Этот контракт отвечает на
вопрос «когда денежной фиче можно верить» — читают бэкенд и оба фронта.
Определения сущностей (закрытая запись, начисление, период) — зона
бэкенд-линии и уточняются там; здесь — критерии готовности.

## Как считается

- **Один канонический расчёт и один авторитетный денежный журнал** на
  каждую сумму. Читающих проекций (ручек, витрин, выгрузок) может быть
  сколько угодно — они только проецируют канонический результат и
  сверяются с ним; второй НЕЗАВИСИМЫЙ способ посчитать «ту же» цифру —
  дефект.
- **Decimal, не float.** Денежная единица, точность, момент и режим
  округления — версионированное доменное правило, одинаковое для любого
  клиента и среды исполнения. Текущее правило: округление один раз, на
  выдаче, HALF_UP — решение владельца 14.08.2026, живёт и тестируется в
  бэкенде; здесь только ссылка, не источник.
- **Результат объясним до записи:** по каждой сумме можно показать, из
  каких записей, ставок и правил она сложилась, и какой версией правила
  посчитана.
- **Детерминизм:** одинаковые входные данные и версия правила дают
  одинаковый результат.
- **Идемпотентность:** повтор операции с тем же ключом не создаёт второго
  финансового эффекта — ни строки начисления, ни повторной выплаты, ни
  сдвига резерва.
- **Аудит append-only:** исправление — новая строка с основанием, не
  правка старой.

## Как меняется

- **Закрытый период не пересчитывается молча.** Исправление в закрытом
  периоде — компенсирующая операция с основанием, видимая в аудите.
- **Смена правила расчёта** проверяется параллельным прогоном старого и
  нового на замороженном наборе данных; допустимый итог — ноль
  необъяснённых расхождений. Каждое объяснённое — записано.
- Бизнес-время — московское; «сегодня» и границы периода называет
  платформа (одна функция часов), локальный системный `today` запрещён;
  у каждого расчёта есть явный расчётный момент. Проверка следствия:
  прогон под Москвой и UTC даёт одинаковый результат.

## Когда готово

Готовность доказывается полным живым циклом, а не зелёными тестами:

```
закрытая запись → начисление → бонусы → заработано → баланс → резерв
→ выплата: частичная оставляет обязательство открытым (выплачено частично),
терминальное «выплачено» — только когда обязательство закрыто полностью
```

Точная машина состояний выплаты (включая отказ и снятие резерва) — контракт
бэкенда; здесь требование: частичная выплата не терминальна, резерв после
неё сходится с балансом.

- Цикл пройден на реальных данных и сверен с внешней правдой (касса,
  банковская операция, ведомость). Допустимый итог — ноль расхождений;
  объяснённое расхождение разбирается по типу: ошибка журнала →
  компенсирующая операция; временная разница (граница периода, банковская
  операция в пути) → открытый пункт сверки до схождения; методологическая
  разница → решение владельца и версия правила. Объяснение само по себе
  не делает баланс готовым.
- Нет расчёта → на экране прочерк, не ноль: ноль значит «посчитали, не
  положено», прочерк — «не знаем».
- Отдельно проверены: частичная выплата; повтор запроса после таймаута;
  отмена и перенос записи; отрицательная корректировка; параллельные
  попытки выплаты; снятие зависшего резерва; сбой между банковской
  операцией и записью статуса; восстановление из бэкапа с
  непротиворечивыми суммами.

## Кто решает

Любое изменение правил денег — решение владельца, подготовленное
бэкенд-линией через согласование с архитектором. Отложить дефект в деньгах
может только владелец.
