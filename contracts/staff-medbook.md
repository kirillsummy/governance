# Контракт: медкнижка сотрудника

Читают: бэкенд (хранит, считает статус, отдаёт), CRM (управляющая заводит,
сверяет, включает публикацию), приложение мастера (мастер вносит и грузит
оригиналы), сайт (показывает факт проверки — и только его). Пишется здесь;
меняется первым — затем стороны, отдельными ветками.

Основание: слово владельца 06.09.2026 (`HANDOFF-2026-09-06-profil-medknizhka-portfolio.md`,
§2–4): «нужна полноценная функция, а не постоянная заглушка», оригиналы
грузят **либо мастер из своего приложения, либо управляющий из CRM**, в обоих
интерфейсах — общие данные одного мастера через бэкенд, без расходящихся
копий. Нормативка — `ИССЛЕДОВАНИЕ-elmk-medknizhka-2026-09-06.md` в корне
рабочего пространства.

**Мастера — самозанятые исполнители на платформе, не работники.** Слово
владельца 06.09.2026 (ответы на вопросы архитектора): «нужно чтобы это
работало как на платформе — чтобы фактически они сами загружали и работали
как самозанятые; закон нужно соблюдать по такому же принципу»; «само понятие
увольнение не может существовать, они работают самостоятельно на платформе».
Следствия для этого контракта: документы и согласия даёт сам мастер из
приложения, платформа их проверяет (как площадки для самозанятых —
«документы проверены»); правовое основание обработки — согласие мастера, а
не трудовое законодательство; вместо «увольнения» — **уход с платформы**
(деактивация в реестре). Требование медкнижки — условие работы на платформе
(оферта), по тем же нормам, что для тех же работ у работников.

## Что уже есть и остаётся

`staff_medbooks` (ревизии 0009, 0098): одна живая строка на человека —
`number`, `issued_at`, `valid_until`, `has_hologram`, `storage_place`.
Управляющая правит её из CRM (`PUT /v1/staff-registry/{staff_id}/medbook`,
актор и след в `staff_registry_audit`), мастер видит в `/v1/profile`
(`medbook`), статус выводится из `valid_until` при чтении: `missing` ·
`expired` · `expiring` (30 дней) · `valid`. Публично не отдаётся ничего —
намеренно (`public_api/schemas.py`).

Этот контракт **достраивает** ту же строку, а не заводит вторую медкнижку.

## Медкнижка — не одна дата, а записи с разными циклами

Владелец называет два срока — «срок медкнижки» и «срок санминимума». По
норме это два разных цикла (исследование, разделы «Коротко» п. 7–8):

    медосмотр (`medical_exam`)          периодический, 1 раз в год
                                        (Приказ 29н, прил., разд. VI, п. 26;
                                        медкабинет — п. 27)
    гигиеническая аттестация            «санминимум», 1 раз в 2 года
    (`hygiene_attestation`)             (Приказ Минздрава 229 от 29.06.2000)

У каждой записи — **две даты**: `passed_at` (прошёл) и `due_at` (следующий
не позже). `due_at` вводится с документа, а не вычисляется: платформа лишь
**подсказывает** умолчание (+365 / +730 дней) в форме, и его можно править —
врачебная организация может назначить иначе.

⛔ **Одного `expires_at` на всё не существует.** Прежнее `valid_until`
остаётся полем **вычисляемым**: наименьшая из `due_at` живых записей —
чтобы список сотрудников в CRM и его отборы продолжали работать без правок.
Писать в `valid_until` напрямую больше нельзя.

⛔ **Номер не делает медкнижку действующей.** Статус — только по записям.

Набор видов записей — закрытый перечень платформы, расширяется ревизией
(прививки, лабораторные — когда владелец скажет). Для двух названных видов
пустая запись = `missing`.

## Документ

    kind          `paper` — бумажная ЛМК · `electronic` — ЭЛМК
                  (оба законны до 01.09.2027; бумага после — по слову нормы,
                  см. исследование)
    number        номер ЛМК / ЭЛМК, как в документе
    issued_at     дата оформления
    has_hologram, storage_place — только для бумажной, как сейчас

СНИЛС платформа **не хранит**: для ручной сверки в реестре ЭЛМК мастер
называет его управляющей при сверке или показывает результат проверки реестра
сам (выписка, снимок экрана — как документ `elmk_extract`). Понадобится
хранить — отдельное решение владельца, это персональные данные повышенного
риска.

## Оригиналы

**Оригинал хранится для сверки; превью оригинал не заменяет.** Слово владельца
06.09.2026.

- Что принимаем: **jpeg, png, webp, heic/heif, pdf**, не больше 20 МБ на
  файл. PDF — потому что выписка ЭЛМК с Госуслуг приходит файлом.
- Что храним: оригинал как прислали (EXIF на месте — он не публичный) плюс
  для картинок веб-копию для просмотра (jpeg, максимальная сторона 2000,
  EXIF срезан) и превью 400. PDF отдаётся как есть.
- Каждый файл привязан к человеку и помечен: `kind` (`lmk_pages` — страницы
  бумажной, `elmk_extract` — выписка/файл ЭЛМК, `other`), `uploaded_by`
  (`master` | `manager`, кто и когда), `note`.
- **У каждого файла — свой статус приёма** (слово владельца 06.09.2026 по
  практике площадок — Яндекс Про, Profi.ru: статус по каждому документу, а
  не одна общая галочка): `pending` — загружен, ждёт; `accepted` — принят;
  `rejected` — отклонён, **с причиной словами** (`review_note`, обязательна).
  Ставит управляющая; мастер видит статус и причину у каждого файла и грузит
  заново — отклонённый файл остаётся в списке помеченным, пока мастер его
  не удалит. Файл, загруженный управляющей, принят сразу.
- **Бакет остаётся приватным, ссылок наружу нет.** Файл отдаётся только через
  авторизованную ручку своего контура (см. «Права»), с `Cache-Control:
  private, no-store`. Публичных, подписанных или угадываемых адресов у
  оригиналов нет: адрес без сессии/токена не открывает ничего.
- Удаление мягкое; файлы остаются в хранилище до отдельного решения о
  сроке хранения (см. «Чего не покрывает»).

Оригиналы медкнижки и работы витрины — одна машина медиа (`media_assets` →
`content_items`, `purpose = document`), разные назначения. Через публичную
витрину документ достать нельзя: она отдаёт только `purpose = portfolio`.

## Источник, автор, сверка

- У каждой записи и у документа — **источник**: `master` (внёс сам из
  приложения), `manager` (управляющая из CRM), `official` (внесено с выписки
  ЭЛМК или после сверки с реестром — ставит только управляющая).
- **Автор и время** каждого изменения — в `staff_registry_audit`, как у
  остальных полей реестра. История append-only.
- **Сверка с оригиналом** — отдельное действие управляющей в CRM: «Сверено с
  оригиналом», с датой, актором и заметкой. Это не автоматическое следствие
  правки: управляющая может внести даты и не сверить. **Сверка невозможна без
  хотя бы одного принятого документа** (`accepted`): подтверждать иначе
  нечем; приём файла и сверка записей — два разных действия, и второе
  опирается на первое.
- ⚠️ **Любая правка номера, вида или дат — сбрасывает сверку.** Мастер
  поправил дату после сверки — медкнижка снова «не сверена», пока
  управляющая не посмотрит. Иначе сверка от прошлого года подтверждала бы
  сегодняшнюю правку.
- **OCR — только помощь вводу**, если появится: распознанное подставляется в
  поля и требует той же сверки. Доказательством актуальности OCR не бывает.
- **Синка из первоисточника нет и не обещается**: у реестра ЭЛМК нет API для
  работодателя (исследование, п. 6). Дорога — ручная сверка + выписка.

## Статусы

Платформа считает и отдаёт, стороны не пересчитывают:

    у записи      missing · expired · expiring (≤ 30 дней) · valid
    у документа   pending · accepted · rejected (+ причина)
    у человека    худший из статусов записей (`status`, как сегодня)
    сверка        `verified_at` / `verified_by` / `verified_note`, либо пусто
    публично      `medbook_checked: bool` — см. «Что видит сайт»

## Напоминания — часть механики

Слово владельца 06.09.2026 (по практике площадок: срок — свойство документа,
площадка напоминает заранее и блокирует в день истечения): напоминания о
сроках — не отдельный заход, а часть медкнижки.

- Платформа считает по каждой записи ступень напоминания от `due_at`:
  `60` (за 60 дней), `30` (за 30), `0` (день истечения и после — «просрочено»)
  и отдаёт её в `records[].reminder` вместе с `due_in_days`.
- **Одна ступень — одно напоминание.** Ступень погашается, когда `due_at`
  сдвинулась вперёд (мастер прошёл осмотр и внёс новую дату) — не по
  «прочитано». Спам из одного и того же напоминания — дефект.
- Где видно: мастеру — в профиле у записи и плашкой на «Сегодня»;
  управляющей — отбор «истекает» и счётчик в списке сотрудников (уже есть,
  работает от `valid_until`). Каналы доставки вне экрана (пуш, Telegram) —
  когда у платформы появится канал; контракт им не мешает и их не обещает.
- Ступень `0` не блокирует ничего сама: рычаг «нет документов — нет
  записи» — этап «позже» (см. «Чего не покрывает»).

## Кто что может

    мастер (своё, `/v1/profile/medbook`)
      читает всё своё, в т. ч. оригиналы;
      правит вид, номер, дату оформления, записи (даты);
      грузит оригиналы; удаляет любой свой документ — это его документ;
      даёт и отзывает согласие на публикацию (см. «Что видит сайт»).
      ⛔ Не ставит сверку, не видит чужого.

    управляющая (`/v1/staff-registry/{staff_id}/medbook`, право `staff`)
      всё то же за любого мастера организации + сверка + удаление любого
      документа; согласие видит, а даёт его мастер (бумажное, данное
      офлайн, может отметить с датой). Владелец — те же права.

⚠️ **Мастер удалил документ, на котором стояла сверка, — сверка снимается**,
как при правке дат: подтверждать больше нечего. Кто и когда удалил — в
аудите; управляющая видит «документ снят мастером».

    сайт (`/v1/public/masters/{staff_id}`)
      только `medbook_checked` (см. ниже). Ни номера, ни дат, ни документов,
      ни статуса записей — никогда, ни в каком поле.

Чужой `staff_id` или `document_id` в приватной ручке мастера — отказ «не
найдено», без разницы между «нет такого» и «не твоё» (как у витрины).

## Что видит сайт

Слово владельца 28.08.2026: медкнижка — в составе публичной страницы, «показываем
ФАКТ, не сам документ». Сегодня вкладка «Медкнижка» на бою у всех «Не
заполнено» — публичной двери нет.

Публичная дверь отдаёт **одно поле**:

    medbook_checked   true — записи в статусе valid/expiring, сверка стоит
                      И у мастера отмечено согласие на публикацию;
                      false — во всех остальных случаях

⚠️ **Согласие — часть правила, а не украшение.** Поимённое «медкнижка
проверена» — распространение сведений о здоровье (специальная категория,
ст. 10 и 10.1 152-ФЗ; исследование, раздел «Персональные данные»). Согласие
на распространение — отдельное, и **даёт его сам мастер в приложении**, как
на площадках для самозанятых: отдельный шаг с текстом согласия, платформа
хранит версию текста, время и кто подписал (`publish_consent_at`,
`publish_consent_version`, `publish_consent_source = master`); отзыв — той
же кнопкой, отзыв сразу даёт `false`. Форма — электронный документ с
электронной подписью мастера по соглашению об электронной подписи в
условиях платформы (ст. 9 ч. 4 152-ФЗ; исследование, раздел «Самозанятые»).
Бумажное согласие, данное офлайн, управляющая может отметить в CRM
(`publish_consent_source = manager`). Без согласия поле `false`, и сайт про
этого мастера молчит.

⛔ **Текст согласия и соглашение об электронной подписи в условиях платформы
— документы владельца и юриста, не разработчика.** Пока их нет, шаг
согласия в приложении не включается, а `medbook_checked` у всех `false`.

Сайт по `true` показывает «Медкнижка проверена» — без дат и номеров; по
`false` не утверждает ничего отрицательного (не «просрочена», не «нет»):
формулировку пустого состояния решает владелец (развилка в вопросах
06.09.2026).

## Ручки

**Своё (мастер, сессия приложения)** — `/v1/profile/`:

    GET    medbook                          документ, записи, статусы, сверка,
                                            список документов
    PUT    medbook                          вид, номер, дата оформления, записи
                                            (частичное обновление, extra=forbid)
    POST   medbook/documents                загрузить оригинал (multipart:
                                            upload, kind, note)
    GET    medbook/documents/{id}/file      файл: size=full | web | preview
    DELETE medbook/documents/{id}           убрать свой документ
    PUT    medbook/publish-consent          {given: bool, version} — дать или
                                            отозвать согласие на публикацию

`GET /v1/profile` продолжает отдавать краткий `medbook` (для шапки профиля),
теперь с двумя записями и признаком сверки.

**Чужое (управляющая)** — `/v1/staff-registry/{staff_id}/medbook`:

    GET    …                                то же, что у мастера
    PUT    …                                то же + has_hologram, storage_place
    POST   …/verify                         «Сверено с оригиналом» {note};
                                            отказ, если нет принятого документа
    POST   …/documents/{id}/review          {status: accepted | rejected, note}
                                            — note обязательна при rejected
    PUT    …/publish-consent                {consent_at | null} — только
                                            бумажное согласие, данное офлайн
    POST   …/documents · GET …/documents/{id}/file · DELETE …/documents/{id}

Существующая `PUT …/medbook` **сохраняет прежние поля** — CRM сегодняшней
версии продолжает работать до своей ветки; новые поля необязательны.

**Публично** — `/v1/public/masters/{staff_id}`: поле `medbook_checked`.

Все ручки — под сервисным токеном, как соседи; мастерские — под сессией
мастера. Прослойка приложения мастера пропускает `/v1/profile/…` по префиксу
— новых записей в белый список не нужно.

## Форма ответа `medbook`

    kind             paper | electronic | null
    number           строка либо пусто
    issued_at        дата либо null
    has_hologram     bool (бумажная)
    storage_place    '' | studio | employee | none (бумажная)
    records          [{ kind: medical_exam | hygiene_attestation,
                        passed_at, due_at, status, source,
                        reminder: { stage: 60 | 30 | 0, due_in_days } | null }]
    status           худший статус записей
    valid_until      наименьшая due_at (совместимость, только чтение)
    verified_at · verified_by · verified_note    либо null
    publish_consent_at · publish_consent_source (master | manager) ·
    publish_consent_version                       либо null
    documents        [{ id, kind, note, uploaded_by, uploaded_at,
                        review_status: pending | accepted | rejected,
                        review_note, reviewed_at, reviewed_by,
                        file_url, preview_url, mime_type }]

## Чего этот контракт не покрывает

- **Срок хранения оригиналов** после ухода мастера с платформы и после
  замены документа — решение владельца; до него файлы остаются, снимаются с
  показа вместе с человеком. Сам мастер может удалить своё в любой момент.
- **Прививки и лабораторные исследования** отдельными записями — когда
  владелец скажет; перечень видов расширяется ревизией.
- **Хранение СНИЛС** и любую автоматическую сверку с реестром — API нет.
- **Каналы доставки напоминаний** (пуш, Telegram, SMS) — сами напоминания
  часть механики (см. «Напоминания»), канал вне экрана появится вместе с
  каналом платформы.
- **Правило «нет актуальных документов — нет записи и показа на сайте».**
  Слово владельца 06.09.2026: этап «позже», после первоначальной загрузки у
  большинства и отдельного включения. Контракт даёт для него сырьё —
  `status` и `verified_at`; сам рычаг, его включение и точки записи (сайт,
  клиентское приложение, диплинки YClients) — отдельный контракт и решение.
  Ручная галочка «Показывать на сайте» (`on_site`) этим контрактом не
  затрагивается.
- **Публичный текст** пустого состояния и наличие даты проверки на сайте —
  вопросы владельцу 06.09.2026.
