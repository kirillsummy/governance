## Ограничения, блокирующие выкладку до решения

1. **Вход CRM.** Production работает с входом `legacy`, общий TEST — `gateway`. В режиме `legacy` недоступны: учёт смен администратора и обязательный экран открытия смены, отчёт об уборке, дежурства, филиалы администраторов, «Моя зарплата» для ролей кроме администратора, удаление рекламации. Нужно решение: переводить production на `gateway` в этом выпуске или выпускать с этими разделами недоступными.
2. **Назначения филиалов.** После перехода на `gateway` администратор без основного филиала смену не откроет. До выкладки нужен список «учётка → филиал», сверенный по ID, и действующие допуски CRM у администраторов.
3. **Совместимость master-app.** Прежний master-app с новым backend при закрытии дня показывает штрафы без предварительного просмотра (зафиксировано при подготовке RC3): master-app выпускается вместе с backend.
4. **Приёмка.** Сценарии SUM-156–158, SUM-164, SUM-165, SUM-176 на TEST в интерфейсе не проверялись; по порядку владельца тесты не проводились.
5. **client-app** в production не развёрнут: его первый выпуск — отдельное решение с собственным адресом и окружением.
6. Штраф по рекламации в ленте заработка мастера после `0149` — открытое решение из RC4.

## Резервная копия

Перед переключением: остановить API и sync production, снять `pg_dump -Fc` на ревизии `0143`, проверить полным чтением `pg_restore -f /dev/null`, записать размер и SHA-256, сохранить действующие compose, `.env` и `VERSION` всех продуктов. Копию хранить вне каталога выкладки. Свободное место на production-сервере перепроверить: 29.09 было 6,7 ГБ.

## Порядок выкладки

1. Утверждение номера и состава; перенос точных SHA в production-ветки без изменения содержимого.
2. Сквозная репетиция `0143 → 0160` на свежем снимке production вне рабочего сервера.
3. Окно: копия БД, backend (`alembic upgrade head`), затем master-app, CRM, website.
4. Назначение основных филиалов и включение флагов — отдельными командами после выкладки, по утверждённым значениям.

## Откат

- До появления данных в новых таблицах: `alembic downgrade 0143_test_developer_access` образом кандидата, затем прежние образы и compose. Прежний backend на новой схеме не стартует, поэтому порядок именно такой.
- Ревизии `0150`, `0158`, `0159`, `0160` отказывают в `downgrade`, когда в их таблицах есть строки (ставки и факты оклада, заявки и документы рабочих мест, заказы доставки, отчёты об уборке, дежурства, назначенные филиалы). После первой такой записи откат схемы возможен только восстановлением копии с потерей данных, внесённых после неё; штатная мера при инциденте — выключить флаг или раздел и оставить совместимый backend.
- CRM, master-app и website откатываются прежними образами независимо от схемы, с учётом п. 3 ограничений.
