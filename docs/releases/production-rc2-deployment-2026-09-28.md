- API и sync: `CASH_PAYOUTS_ENABLED=false`, `PHOTO_PROOF_V2_ENABLED=false`.
  Действующие начисления и история сохраняются; новые cash-запросы и
  фотоштрафы закрыты. Канон — [cash](../../contracts/cash-earnings-payout.md)
  и [закрытие визита](../../contracts/appointment-closure-photos.md).
- API: production environment, TEST-вход, orders-test, master booking,
  client portal и platform-id выключены. Для сохранённого legacy CRM
  `CRM_SESSION_REQUIRED=false`, `PROCESS_SESSION_REQUIRED=false`;
  `INTERNAL_MASTER_API_ENABLED=1` сохранён.
- CRM: `ADMINAPP_AUTH_PROVIDER=legacy`, `ADMINAPP_YCLIENTS_AUTH_MODE=live`,
  `ADMINAPP_LEGACY_PROCESS_LOOKUPS_ENABLED=true`, orders/test-developer
  выключены. Прежние пользователи, роли и права не заменялись gateway grants.
- Master: `VITE_ORDERS_TEST_ENABLED=false`, `VITE_PLATFORM_ID_ENABLED=false`,
  `VITE_API_BASE=/`; runtime TEST-вход выключен.
- Website: `NEXT_PUBLIC_CLIENT_BOOKING_ENABLED=false` при сборке,
  `STAND_PRIMERKA` отсутствует; запись направлена в YClients.
- Новые внешние уведомления не включены; production env не заменён TEST env.

Реальный пользовательский вход, платёж, SMS, выплата, отправка рекламации
и записывающие внешние вызовы в этой выкладке не выполнялись. Успешные health
и безопасные HTTP-пробы не объявляются приёмкой этих сценариев.

  `/root/releases/rc2-20260928/stage/{backend,crm,master}`.
- Прежний website целиком: `/var/www/.summy-rc2-swap-20260928`.
- Предыдущие образы: `summy-backend-api:pre-rc1-20260928`,
  `summy-backend-sync:pre-rc1-20260928`, `summy-crm:pre-rc1-20260928`,
  `summy-master:pre-rc1-20260928`.

Frontend можно вернуть сохранённым образом/деревом через ту же действующую
конфигурацию, затем перепроверить версии и public health. Сначала сверить
сохранённый артефакт и env; `compose down` не является восстановлением.

**Совместимость старого backend с уже мигрированной production-БД 0143
runtime-проверкой не подтверждена.** Возвращать API/sync автоматически
нельзя: требуется проверка ревизии, совместимости читателей и данных.
При проблеме предпочтительно исправление вперёд; restore/downgrade допускаются
только по отдельно проверенному плану, с учётом новых записей после релиза.
