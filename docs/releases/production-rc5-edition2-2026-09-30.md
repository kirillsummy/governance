## Совместимость с действующим входом production

Production работает со входом CRM `legacy`: допуск задаётся списками номеров учёток YClients в окружении CRM, пароль проверяет YClients. Кандидат работает в обоих режимах; режим выбирается аргументом `--crm-auth` и других прав не меняет.

- **`legacy`** — доступ всех текущих пользователей сохраняется как есть. Разделы, которым нужна серверная сессия (обязательное открытие смены, отчёт об уборке, дежурства, филиалы администраторов, «Моя зарплата» для ролей кроме администратора, фильтр ответственного, удаление рекламации), в CRM не показываются и не запрашиваются; backend оставляет `CRM_SESSION_REQUIRED` и `PROCESS_SESSION_REQUIRED` выключенными. Вход mock или тестовый вход не используются.
- **`gateway`** — те же учётки с тем же паролем YClients. Шаг `access` переносит в `gateway_admin_access` ровно действующие списки из окружения CRM: те же номера и те же роли, существующие строки не меняются, при расхождении роли или выключенном допуске скрипт отказывает без записи. Управляющей и администраторам выдаётся допуск к обоим действующим филиалам — как в `legacy`, где ограничения по филиалу нет. Новые учётки не создаются, роли по имени не выдаются, логины и пароли TEST не переносятся. Каждая запись попадает в `auth_audit`.

## Команды переключения

Всё выполняется от root на production в окне без записи, вне 04:20–04:40 МСК (ночная копия БД и медиа). Каждая фаза берёт блокировку `/var/lock/summy-production-release.lock` и отказывает при параллельной выкладке; журналы — в `/root/releases/rc5-20260930/logs` (права 0600), в вывод секреты не попадают.

0. После утверждения: перенести точные SHA из таблицы в production-ветки fast-forward, без изменения содержимого. Скопировать `release/` с TEST в `/root/releases/rc5-20260930` (права 0700). Проверить `sha256sum -c SHA256SUMS` для скопированных файлов.
1. `python3 rc5-stage.py --crm-auth <legacy|gateway> [--cleaning-admin-report-from YYYY-MM-DD] [--manager-pay-approver <ID>] [--settings-nav-hidden-login <ID>]` — проверяет, что backend, CRM и master-app на RC2; загружает образы, сверяет SHA-256 архивов и метку ревизии, удаляет архивы; готовит каталоги `stage/` с копией действующих `.env` и compose, где меняются только образ и перечисленные флаги (порты, сети, тома, команды, healthcheck — сверяются); службы не трогает.
2. `python3 rc5-website-stage.py` — распаковывает сайт рядом с действующим каталогом, сохраняет `.env.local`, сверяет `BUILD_ID`, проверяет, что оператор и стенд выключены.
3. `echo 'RC5 approved; all artifact gates passed' > RELEASE_GO` — только после утверждения.
4. `python3 rc5-deploy.py backend` — сверяет образ работающих API и sync с RC2; останавливает API и sync; снимает базовую линию БД; делает свежую копию `summy-db-backup.sh`, читает её полностью `pg_restore --file=/dev/null`, пишет размер и SHA-256 в `fresh-db-backup.json` и кладёт копию в `snapshots/`; меняет каталог атомарно (`renameat2`); применяет семнадцать ревизий по одной к действующей БД без restore; сверяет прежние данные; запускает API и sync и ждёт `ready` и версию.
5. Только для `gateway`: `python3 rc5-deploy.py access` — перенос допусков по номерам и назначение основных филиалов; если хоть один администратор из списка остался без филиала, фаза падает и CRM не переключается.
6. `python3 rc5-deploy.py master`, затем `python3 rc5-deploy.py crm`, затем `python3 rc5-deploy.py website` — атомарная замена каталога, `up -d --no-build` (сайт — перезапуск pm2), ожидание health с точной версией; при неудаче фаза сама возвращает прежний каталог.
7. `python3 rc5-postdeploy-check.py --after db-before.json --crm-auth <режим>` — только чтение: SHA и версии, ревизия `0160`, флаги, выключенные фоновые задачи, новые маршруты и таблицы, для `gateway` — основной филиал у каждого администратора.
8. client-app — по [границе client-app](#граница-client-app): поставка кода безусловно, включение входа только при наличии runtime-конфигурации.

Сборок на production нет. Пик занятого места — около 2,4 ГБ (каталог выпуска, загруженные слои, свежая копия БД с дублем в `snapshots/`). Скрипты требуют больше 4 ГиБ свободного места до `stage` и 3 ГиБ до каждой фазы; при чтении 30.09 было 6,24 ГиБ. Прежние образы не удаляются.

## Копия и откат

- Ночные копии 30.09: БД в 04:20 (44 347 978 байт, полное чтение `pg_restore` прошло: 181 таблица с данными), медиа в 04:30 с второй копией. Перед миграцией фаза `backend` снимает и проверяет отдельную свежую копию при остановленной записи.
- Ошибка миграции при остановленной записи: фаза `backend` сама возвращает схему в `0143` образом кандидата, возвращает прежний каталог и запускает RC2. Это единственный автоматический `downgrade`; новых данных в этот момент нет.
- После запуска RC5 автоматического `downgrade` и restore нет. `rc5-deploy.py rollback-backend` работает только до шага `access` и до переключения master-app и CRM; после назначения филиалов откат схемы — отдельное решение о данных.
- `rollback-website`, `rollback-crm`, `rollback-master` возвращают прежний каталог с прежними compose, `.env` и образом и ждут health RC2. Прежний master-app с новым backend показывает штрафы при закрытии дня без предварительного просмотра, поэтому откат master-app при оставленном backend RC5 — осознанное решение.
- Штатная мера при инциденте после появления данных — оставить backend RC5 и выключить раздел или флаг.

Одно утверждение «RC5 редакция 2» покрывает пять SHA из таблицы и следующие значения. Все они уже согласованы в поручениях; открытых решений, кроме самого утверждения и окна выкладки, нет.

| Параметр | Значение |
|---|---|
| Вход CRM | `--crm-auth gateway`: действующие пользователи и роли из списков допуска CRM переносятся по номерам учёток, новые учётки не создаются, сопоставления по имени нет |
| Основные филиалы администраторов | `primary-locations.json`: пять действующих учёток администраторов, сверенных по номеру учётки и рабочему месту сотрудника в справочнике; без сверки фаза `access` останавливает выкладку до CRM |
| Утверждающий факты оклада управляющей | `--manager-pay-approver` — учётка действующего владельца из списка допуска (номер — в SUM-176) |

## Граница client-app

Адрес `https://summy.ru/client/` и тексты согласий существуют. SMS для клиентского входа настраивались ранее и работали; дополнительная проверка SMS отменена поручением и условием выпуска не является.

1. **Поставка кода — безусловно, в том же окне после фазы `website`.** Образ `summy-client:rc5-175633fa52b4` загружается из `images/client-rc5.image.tar.gz` со сверкой SHA-256 и метки ревизии; `client-app-compose.prod.yml` и `client-app-nginx-location.conf` кладутся в `/opt/summy-client` неактивными. Контейнер не запускается, `location /client/` в nginx не добавляется, `CLIENT_PORTAL_ENABLED` в backend остаётся `false`. Для пользователей ничего не меняется.
2. **Первое включение входа — только если на production уже есть runtime-конфигурация.** Перед включением проверяется лишь наличие непустых ключей, без вывода значений: `.env` client-app в `/opt/summy-client`, `CLIENT_PORTAL_SECRET` и настройки уже действующего SMS-провайдера в `.env` backend. Если всё есть — в backend включается `CLIENT_PORTAL_ENABLED=true` (пересоздание API и sync без миграций), запускается контейнер на `127.0.0.1:5191` и добавляется `location /client/`. Провайдер, отправитель и платные настройки по предположению не выбираются и не создаются; тестовые SMS не отправляются.
3. **Если конфигурации нет** — шаг 2 не выполняется, в отчёте о выкладке фиксируется «client-app: код поставлен, клиентский вход не включён», выпуск остальных четырёх продуктов этим не блокируется. Включение позже — той же командой шага 2, как только конфигурация появится на сервере.
4. **Откат client-app** — удалить `location /client/`, остановить контейнер и вернуть `CLIENT_PORTAL_ENABLED=false`; данные и схема не затрагиваются.
