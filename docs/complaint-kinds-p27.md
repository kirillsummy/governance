## 1. Что уже есть

### Поля классификации рекламации

Рекламация — строка `processes` с `type='complaint'`; поля анкеты в
`processes.fields` (jsonb), словари — в `process_types.fields[].options`.

| Поле | Подпись | Значения сейчас | Откуда |
|---|---|---|---|
| `defect_kind` | «Вид брака» | закрытый список из 19 значений (ниже) | миграция `0110_slovari_reklamacii`; платформенный дефолт `DEFECT_KINDS` в `app/domains/processes/workflows.py` |
| `special_case` | особый случай | «Вред здоровью», «Негативный отзыв на площадке» | `SPECIAL_CASES` |
| `appeal_category` | «Категория обращения» | «Качество», «Сервис», «Отзыв» | `0110`; `APPEAL_CATEGORIES` |
| `appeal_source` | «Источник обращения» | «Лично в студии», «Мессенджер», «Внешняя площадка (отзыв)» | `0110`; новая форма CRM его не спрашивает |
| `service_category` | «Направление» (в карточке CRM — «Категория услуги») | снимок имени категории услуги из каталога | анкета `0067_complaint_decision`; заполняет backend |
| `service_name` | услуга | снимок названия | backend |
| FK `processes.service_id` | — | стабильная услуга каталога | `0125_complaint_canonical_model` |

Индексы по полям анкеты (0125): `appeal_source`, `appeal_category`, `defect_kind`,
`special_case` и поля решения; по `service_category` индекса нет.

### Группы видов брака по категории услуги (`complaint_defect_rules`)

Группировка уже существует — в коде backend `DEFECT_RULES`
(`app/domains/processes/complaints.py`), отдаётся в каноне
`GET /v1/processes/workflows` как `complaint_defect_rules`
(`category_keywords`, `defect_kinds`). Название группы как значение не хранится —
только ключевые слова.

| Неявная группа | Ключевые слова | Виды брака |
|---|---|---|
| Маникюр / педикюр | `маникюр`, `педикюр`, `ногт` | Скол · Отслойка · Трещина · Дефекты покрытия · Онихолизис · Синегнойка · Пропилы |
| Ресницы | `ресниц` | Отвалились ресницы · Склейка ресниц · Несоблюдение рядности · Несоблюдение направления · Покраснение глаз · Ожёг (ресницы) · Не понравился эффект ламинирования |
| Брови | `бров` | Не понравился цвет · Не понравилась форма · Ожёг (брови) |
| Лазерная эпиляция | `лазер` | Ожёг (ЛЭ) |
| Депиляция | `депил` | Не понравился эффект ДУ |

Группы совпадают со стартовым словарём Аспро (приложение `contracts/reklamaciya.md`):
«маникюр/педикюр, ресницы, брови, ЛЭ, ДУ». Шесть сервисных значений Аспро в `0110`
перенесены в `appeal_category`/`appeal_source`.

### Как работает выбор (SUM-119, поставлен)

- Категория услуги: визит → позиция → `service_offers` → `services.category_id` →
  `service_categories.name` (зеркало каталога YClients); снимок пишется в
  `service_category`. Дверь «без визита»: услуга из каталога (`service_id`) даёт
  категорию так же; без услуги CRM предлагает свободный ввод «Категория услуги (если
  известна)» и «Название услуги со слов клиента».
- Сопоставление: первое правило, у которого ключевое слово входит подстрокой в
  «`service_category` + `service_name`» (без регистра). Прямая категория, без обхода
  родительских категорий.
- CRM (`src/domain/process/complaint.ts complaintKindChoices`,
  `src/components/kanban/complaint-create.tsx`): одно видимое поле «Вид рекламации» =
  виды брака группы услуги ∩ настроенные опции `defect_kind` + «Сервис: общение,
  запись, отмена» (`appeal_category=Сервис`) + «Особый случай: …». Если вариантов нет —
  явное сообщение «справочник платформы не предлагает вариантов для этой услуги».
- Сервер (`require_matching_defect`, `derive_appeal_category`): при создании, правке и
  привязке визита несовместимый вид → 422 `complaint_defect_service_mismatch`;
  одновременно `defect_kind` и `special_case` → 422 `complaint_kind_conflict`;
  `appeal_category` выводится: брак → «Качество», особый случай → по словарю
  («Вред здоровью» → «Качество», «Негативный отзыв на площадке» → «Отзыв»).
  Сохранённые карточки не переписываются.
- Отображение: карточка CRM показывает «Категория услуги»; список — столбец «Вид
  рекламации» (`defect_kind || special_case || appeal_category`); фильтры рекламаций —
  `defect_kind`, `appeal_category`, `appeal_source`, `resolution_kind`, ID услуги
  (текстовое поле), мастер, клиент, телефон, даты. Фильтра по категории/группе услуги
  нет ни в CRM, ни в `GET /v1/processes`.
- Клиентское приложение вид не выбирает (только услуга недавнего визита, описание, фото).

## 2. Что уже покрывает пожелание владельца без нового кода

- «Маникюр» и «Брови» уже являются группами видов брака: при услуге из категории с
  «маникюр»/«бров» в названии форма показывает только виды своей группы, сервер
  отклоняет чужие.
- У каждой карточки, заведённой по визиту или услуге каталога, сохранена категория
  услуги (`service_category`) — она видна в карточке и не переписывается.
- Сервисные обращения и особые случаи отделены от брака (`appeal_category`,
  `special_case`) и доступны для любой услуги.
- Дверь без визита: ввод «Маникюр»/«Брови» в «Категория услуги» открывает
  соответствующую группу.

Если владелец под «категорией» имел в виду именно это, P27 закрывается подтверждением
и, при желании, мелкими улучшениями видимости (вариант А ниже).

## 3. Пробелы и риски текущей реализации (факты)

1. **Группа не имеет имени и ID.** В данных и API есть только ключевые слова; CRM не
   может подписать «Маникюр: Скол» или сгруппировать список по направлениям.
2. **Справочник рассогласован с правилами.** Опции `defect_kind` владелец может
   менять в настройках вида (`app/domains/processes/types.py`: для полей рекламации
   допускаются любые непустые уникальные значения), а `DEFECT_RULES` — константа кода.
   Новый вид брака, добавленный в настройках, не попадёт ни в одну группу: CRM его не
   покажет, сервер отклонит. Переименование вида разрывает группу. Это расходится с
   каноном «словари правит владелец в CRM» (`reklamaciya.md`, «Словари — где живут»).
3. **Сопоставление по подстроке прямой категории.** Если услуга лежит в подкатегории
   без ключевого слова (а «Маникюр» — родитель), виды брака не предложатся, если их нет
   и в названии услуги. Для формы закрытия SUM-113 уже принят другой способ — обход
   родительских категорий с точным именем «Маникюр»
   (`master_cabinet/service.py`). Реальные имена категорий каталога не проверены.
4. **Педикюр объединён с маникюром** в одной группе — входит ли он в «Маникюр»
   владельца, не подтверждено.
5. **Нет отчёта/фильтра по направлению**: ни параметра API, ни индекса по
   `service_category`.
6. **Свободный текст категории** в двери без визита допускает опечатки и
   несопоставимые значения.

## 4. Две трактовки «категории» (SUM-96 № 58) и минимальный безопасный шаг

Инварианты для обоих вариантов (план P27, решение 02.10): `appeal_category` не
заменяется на «Маникюр/Брови»; второй справочник без решения не вводится; старые
карточки и история не переписываются; классификация не меняет сроки, ответственного,
компенсации и штрафы; SUM-119 не делается заново; YClients и деньги не затрагиваются.

### Вариант А — «категория» = категория (направление) услуги

Смысл уже реализован неявно (§1). Нужна видимость и управляемость, а не новая ось.

- **Шаг А0 (без кода).** Показать владельцу таблицу групп из §1 и получить
  подтверждение состава: какие направления, входит ли педикюр в «Маникюр», нужны ли
  группы для услуг вне пяти направлений (сейчас им доступны только «Сервис» и особые
  случаи).
- **Шаг А1 (аддитивно, без миграции).** Добавить в `ComplaintDefectRuleView`
  необязательное поле названия группы (`label`) и показывать в CRM виды с группировкой
  (`optgroup`) и подписью направления в списке. OpenAPI расширяется аддитивно,
  `contract_v1` не затрагивается; старая CRM продолжает работать.
- **Шаг А2 (аддитивно, без миграции).** Фильтр списка рекламаций по направлению:
  новый необязательный параметр `GET /v1/processes` по снимку `service_category`
  (по ключевым словам группы) + выбор в «Фильтрах рекламаций». Индекс — отдельным
  решением при необходимости.
- **Требует решения, не делать молча:** переход на обход родительских категорий
  (меняет набор доступных видов для части услуг); вынос `DEFECT_RULES` в данные,
  редактируемые владельцем (миграция, канон словарей), — снимает пробел 2;
  замена свободного ввода категории в двери без визита на выбор из каталога.

### Вариант Б — «категория» = отдельная новая ось рекламации

Не связана с услугой (например, собственная классификация владельца поверх вида).

- **До решения кода нет.** Нужны: полный список значений и стабильные коды, кто ведёт
  справочник, обязательность, поведение для двери без визита и для сервисных
  обращений/особых случаев, соотношение с `appeal_category` (сосуществуют, не
  заменяют), нужен ли отдельный UI поверх одного поля «Вид рекламации», значение для
  старых карточек («не указано», без обратного заполнения).
- **Минимальный безопасный шаг после решения.** Одно новое необязательное поле
  анкеты рекламации, добавленное миграцией по образцу `0110` (дописать в
  `process_types.fields`, только если поля нет; правки владельца не стираются;
  обратимый downgrade удаляет только это поле из анкеты), опции редактируются в
  настройках вида, сервер проверяет принадлежность значению из опций, CRM показывает
  поле в форме и фильтре. Без обратного заполнения и без влияния на `defect_kind`,
  `special_case`, `appeal_category`, сроки и деньги.
