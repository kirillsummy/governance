# Правила разработки и проверки

Свод технических соглашений и каталог проверок перед Prod. Полномочия и
обязательные правила — в [уставе](../CHARTER.md); этот файл их не расширяет.
Продуктовые особенности ниже нельзя автоматически распространять на все
репозитории.

## Границы сторожей Governance

`check-canon.mjs` читает локальные деревья, не remote refs; до вывода о GitHub
нужна свежая сверка веток. Перед живой проверкой он подтверждает собственные
отрицательные случаи; недоступный GitHub при проверке default branch означает
«не проверено», а `--no-remote` — только явно локальный прогон. Побайтовая
копия guard обязательна для backend/CRM, но не для быстрых jobs website и
master-app. `check-docs.mjs` проверяет локальные файлы и каталоги, не внешние
URL или якоря.
Проверка копий сравнивает текст после нормализации CRLF→LF: Git хранит эти
файлы одинаково, хотя Windows checkout может дать разные переводы строк.
Любое другое расхождение остаётся ошибкой. Разбор таблицы веток принимает
текущий заголовок `Default/базовая ветка`; отрицательный самоизлом изменяет
все такие заголовки, чтобы проверить реальный отказ парсера.

`uzhe_proveren.py` получает имя полной CI-job из окружения workflow: равное
дерево без действительно зелёной полной job не является доказательством
проверки; отсутствующее настроенное имя job даёт отказ. Карантинный сторож
читает срок из имени папки по календарной дате Москвы, предупреждает за три
дня, после срока завершает проверку с ошибкой и требует опись владельцу;
ничего автоматически не удаляет. Несуществующая дата вроде 30 февраля и
папка с опечаткой, но содержащая `karantin`, тоже должны дать ошибку, а не
обойти проверку. CI сначала проверяет отрицательный случай, затем живые папки.

## Каталог проверок по затронутому продукту

Команды ниже — справочный каталог, а не разрешение на запуск. Политика запуска —
в [уставе](../CHARTER.md#проверки-и-ci): прогоны проводятся при подготовке
Prod или по явному запросу, а не при разработке и доставке на Dev.

| Продукт | Команды из памяток/manifests |
|---|---|
| backend | `pytest -q` с PostgreSQL; `ruff check app tests`; `mypy app tests`; денежные сценарии в UTC и Europe/Moscow; миграции и db/verify.sql при изменении схемы |
| client-app | `npm test`, `npm run build`, `npm run format:check` |
| master-app | в web: `npm run typecheck`, `npm test`, `npm run build`, `npm run check:palette`; из корня `node --test bff/server.test.mjs` |
| CRM | `npm test`, `npm run typecheck`, `npm run lint`, `npm run build` |
| website | `npm run build`, `npm run lint`, `npm run check:palette`; отдельный test script в просмотренном manifest отсутствует |
| governance / DOC | Относительные ссылки, источники и SHA, непротиворечивость статусов, отсутствие секретов, git diff --check; релевантный сторож канона по его инструкции |

Не повторять дорогой прогон без новой причины. Зелёный pytest с пропущенной БД не доказывает
корректность денежных сценариев. Здесь менялась только документация: эти команды
перечислены для следующих задач, а не заявлены повторно выполненными 19.09.

## Проверка межпродуктового изменения

1. Определи хозяина данных, всех читателей и версию контракта.
2. Проверь auth/ownership, allowlist BFF, DTO, отключённый флаг и поведение ошибки.
3. При изменении БД проверь совместимость старого клиента и обратный путь без удаления аудита.
4. Сверь бизнес-время, идемпотентность и неоднозначные внешние ответы.
5. Зафиксируй порядок PR/миграций, точные SHA, проверки, незавершённое и пределы демо.

Пункты выше сведены из действующих правил, а не разрешают самостоятельный релиз.
Рекомендация, пока не реализованный механизм: автоматизировать проверку DOC-ссылок
и обновление снимка веток отдельной CI-задачей после согласования. Постоянный job
и новый «полный аудит» этим изменением не добавляются.

Дополнительные предложения из PR #64, требующие отдельного внедрения:

- Автоматическая сверка БД, VIEW, OpenAPI и клиентских контрактов основных веток.
- Единый набор ролей и отрицательных сценариев доступа через реальные входы.
- Воспроизводимые конфигурации общего стенда вместо оставшихся серверных переопределений.

CI backend уже проверяет доступность PostgreSQL перед pytest; локальные пропуски
БД-тестов не означают отсутствие такой проверки в CI. Полный набор инструментов
CI включает также vulture и deptry; перед запуском сверять текущий workflow.


## Принципы проверки и записи

Правила, проверенные двумя случаями из разных рук (собраны 18.08–07.09.2026,
слово владельца 18.08.2026; прежде — раздел устава). Применяются там, где
проверка проводится: при подготовке Prod, по явному запросу и при сверке
фактов доставки.

**Прибор.**

1. **У прибора три ответа: да, нет, не знаю** — и «не знаю» закладывают при
   постройке: спроси, чем проверка отзовётся, если сломать её саму; отзовётся
   успехом — прибор негоден. Тишина прибора и ответ чужого API на мусор — тоже
   «не знаю»: проверяй состояние мира, а не вывод. Красному задают тот же
   вопрос — от того ли оно.
2. **Предохранитель проверяют изломом** — сломай каждое место, которое он
   обещает охранять; не покраснел — предохранителя нет. **Прибор доказывает
   себя при каждом прогоне**, а не когда о нём вспомнят: самоизлом до живого
   суда, без сети. Изломы — только на закоммиченном; ломать то, что вернёт
   команда, а не память.
3. **Прибор настраивают только при числе**: прежде чем крутить ручку — заведи
   число, которое она должна сдвинуть.
4. **Свежесть службы доказывает то, что отдаёт служба** — схема, версия,
   поведение; не база, не лог миграции, не имя ветки.
5. **Механизм построен ≠ данные приведены**: спроси, есть ли хоть одна строка,
   где механизм сработал.
6. **Перед выводом назови единицу измерения** и проверь, не исчезает ли в ней
   та разница, о которой вопрос: час против суток, компонент против сводки,
   «дверь» против «приёмной».
7. **Отрицательный вывод проверяют как положительный**: «не нашёл» — «нет там,
   где я смотрел». Прибор отвечает на свой вопрос — проверь, на тот ли.
8. **Невидимая внешняя настройка — часть системы**: что влияет на поведение,
   названо в каноне и проверяемо прибором (главная ветка GitHub, панель
   провайдера).

**Бумага.**

9. **У замера четыре части: что мерили, чем, что получилось, чьё.** Пересказ
   повышает замер в звании — чужое число сверяют у источника, прежде чем на
   нём строить.
10. **Проверяй постановку, не только исполнение**: жив ли замысел в базе,
    существует ли то, что объявлено сломанным; совпадение по времени — не
    связь.
11. **У контракта есть граница, и она пишется** строкой «чего он не
    покрывает»; молчание документа — не «здесь всё».
12. **У цитируемого правила должен быть адрес** — файл и строка; нет адреса —
    сначала запиши, потом исполняй. Записывай у точки действия, в канон —
    только шире одного продукта.
13. **Имя обещает не больше, чем делает тело**: опираешься на имя — открой
    тело или проверь пробой; мёртвое поле хуже отсутствующего.
14. **Второй источник — почти-копия, не копия**: спрашивай «откуда значение и
    есть ли второе место»; вывод — из единственного источника с проверяемой
    связью; копию прибора — по отпечатку, продуктовое отличие — в окружение.
15. **Письмо описывает прошлое** — перед действием сверь живое состояние.

**Ветки и поверхности.**

16. **Сначала схема, потом службы** — порядок выкатки; инструкцию, собранную
    по репозиторию, вычитывает тот, кто выкатывал руками.
17. **Незапушенное не касается общих поверхностей**: перед накатом на общий
    стенд или базу — пуш; свободный номер ревизии проверяют по origin и по
    всем базам машины.
18. **Исходная ветка после переноса снимается**: уникальные коммиты сначала
    включают в `test` либо сохраняют архивным тегом;
    опубликованную историю не переписывают.

### Чем отчитываются о проверке

Результат показывают вместе с основанием: **сколько** проверено, **откуда** и
**с каким фильтром**. «Прошло» без числа проверенного — не результат. Каждая
приставка лечит свою ошибку:

- **с каким фильтром** — спросили не то: число честное, вопрос неверный;
- **откуда** — ответил не тот: SPA-фолбэк вместо сервиса, чужая копия на том
  же порту, дата образа вместо содержимого контейнера;
- **сколько** — проверять было нечего: тесты «прошли» на нуле файлов, сверка
  сошлась на нуле строк.

Усечение вывода (`head`, `limit`, «первые N») — тоже фильтр, самый незаметный.
`getattr(..., None)` делает «колонку забыли» неотличимым от «значения нет».
Свежесть образов мерят содержимым работающего контейнера, а не датами образа.
Парное правило — седьмое в «Приборах и бумагах»: проверь, на тот ли вопрос
ответил инструмент. Случаи 17.08.2026 — в
[истории](history/charter-cases-2026-08.md).
