# Технические решения ревизии вопросов: D01–D13

Дата: 03.10.2026. Источник — ревизия открытых вопросов 03.10.2026 по прямому
поручению: вопросы, которые команда решает сама, сняты с владельцев и
превращены в технические решения о способе реализации. Это решения команды
(Codex, исполнение — Claude), не бизнес-ответы Кирилла или Юры и не
доказательство готового кода. Ход работы — [SUM-203](https://summy.youtrack.cloud/issue/SUM-203),
поставленные строки — [SUM-210](https://summy.youtrack.cloud/issue/SUM-210).

Не разблокировано этими решениями: новые денежные и кадровые правила,
расширение прав, недоступные внешние доступы, палитра видов процессов
(SUM-97 Q207-1), истёкший карантин CRM (SUM-96 № 76), production.

## Решения

| № | Источник | Решение |
|---|---|---|
| D01 | QA-6.1 | Разрешённые филиалы проверяет backend перед созданием и изменением заказа; проверка CRM дополнительная. Неподходящая тестовая фикстура исправляется под контракт, серверная защита не ослабляется. Новых выдач не делать. |
| D02 | QA-6.2 | Заявки переноса и отмены и их дедупликация принадлежат общему серверному контуру. При конфликте сторона получает допустимую для неё ссылку на существующую заявку; CRM, клиент и мастер учитывают один факт. Чужой процесс через `process_id` не открывается, второго денежного контура нет. |
| D03 | QA-5.2 | Публичный QR-адрес имеет серверное ограничение частоты, проверку входа и короткую ссылку от заданного публичного адреса. Сканирование — техническое событие, не начисление и не подтверждение личности. |
| D04 | QA-5.1/3 | Канонический источник филиалов сайта один; индекс под `record_external_id` выбирается по текущей схеме и запросу. Индекс не вводит уникальность или новое правило оплаты без оснований. |
| D05 | QA-2 | Согласованная задержка премий считается по смене, а не по календарному дню. Хранение санкции администратора проектируется совместимо с действующим аудитом; таблица штрафов мастеров не доказывает зарплатный эффект администратора. Новые размеры и основания штрафа не вводятся. |
| D06 | QA-3 | Связь CRM-субъекта и сотрудника — только подтверждённая серверная связь существующих сущностей. Отсутствие связи — явное состояние, не склейка по имени или телефону и не выдача роли. Панель смены и обжалование — по уже действующим полномочиям. |
| D07 | QA-4/6 | Схемы, OpenAPI, generated-типы и снимки миграций приводятся к точному доставленному составу. Проверки — по фазе канона; разрешение на проверки RC не переносится на тестирование живого Dev. Бизнес-правила ради зелёных тестов не меняются. |
| D08 | QA-6.3/4/5 | Планировщик включается в штатный реестр; повтор одного события не создаёт новую карточку. Оптимизация клиентского цикла не меняет формулу статуса. Для отзыва предпочтителен стабильный ID источника; хеш вложения сам по себе не доказывает отдельный отзыв. |
| D09 | SUM-96 № 29 | Мастер получает ограниченную проекцию связанной рекламации — уже утверждённые статус, история и обжалование; не весь внутренний `ProcessDetail` и не дополнительные персональные поля. |
| D10 | SUM-96 № 38/49 | ТЗ составляется по доступным подтверждённым источникам; визуальные решения — по существующей дизайн-системе с показом конкретного результата. Недоступные материалы остаются адресными запросами. |
| D11 | SUM-96 № 46/75 | Старый прайс сравнивается с каноном и сохраняется архивом без удаления; происхождение записи подписывается по подтверждённым фактам, автор записи YClients не угадывается. |
| D12 | QA-1 | Сначала исследуются официальная документация и действующий read-only адаптер абонементов и депозитов; спрашивается только недостающий доступ или конкретная неподтверждённая возможность. YClients не изменяется. |
| D13 | Q24-7/10/11 | Chatwoot — первый кандидат: серверный адаптер и своё окно CRM, Application API для оператора, проверка текущих прав на каждой операции. Транспорт и архитектуру выбирает команда; экземпляр, каналы, согласия и доступы требуют фактов. Telegram-бот не выдаётся за поддержку личного аккаунта. |

### D12 — абонементы и депозиты YClients: официальная документация (03.10.2026)

По публичной документации `developers.yclients.com/ru/` (чтение страницы, без
обращений к API):

| Данные | Метод | Авторизация |
|---|---|---|
| Абонементы клиента по телефону | `GET /api/v1/loyalty/abonements/?company_id=&phone=` | bearer user |
| Личные счета (депозиты) клиента филиала | `GET /api/v1/deposits/company/{company_id}/client/{client_id}` | bearer user |
| Личные счета клиента по сети | `GET /api/v1/deposits/chain/{chain_id}/phone/{phone}` | bearer user |
| История счёта | `GET /api/v1/deposits/chain/{chain_id}/deposit_history/{deposit_id}` | bearer user |
| Типы абонементов филиала | `GET /api/v1/company/{company_id}/loyalty/abonement_types/search` | bearer user |

Все — чтение; запись в YClients не нужна. Действующий read-only allowlist
backend (`app/integrations/yclients/read_only.py`) этих путей не содержит, а
документация называет базу `api.yclients.ru`, тогда как адаптер разрешает
`api.yclients.com/api/v1` — при подключении это сверяется. Недостающее —
только факт доступа: есть ли у пользователя интеграционного токена права на
абонементы и личные счета и что вернёт одно чтение по тестовому клиенту
(учётка Кирилла Данилова). Это остаётся адресным вопросом к владельцу доступа
(SUM-97 QA-1); адаптер не расширялся.
