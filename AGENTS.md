# SUMMY · вход для агента

SUMMY — платформа сети студий услуг: публичный сайт, CRM сотрудников, приложение мастера и разрабатываемое клиентское приложение. Общие данные и продуктовая логика принадлежат одному backend. Этот публичный репозиторий — центральный **DOC**: карта системы, правила и межпродуктовые контракты.

## Первые 5–10 минут

1. Прочитай [CHARTER.md](CHARTER.md): это L0, роли, полномочия и релизный процесс. Эта памятка его не заменяет.
2. [Продукт](docs/product.md) → [текущее состояние](docs/current-state.md) → [архитектура](docs/architecture.md). Статусы «код», «тестовая ветка» и «проверено на проде» различаются.
3. Выбери [репозиторий](docs/repositories.md), затем его **актуальный** AGENTS.md, README и документы затронутого домена.
4. Для стыков прочитай [API](docs/api.md), [БД](docs/database.md) и соответствующий [контракт](contracts/). Для адресов — [ресурсы](docs/resources.md).

## Архитектурные ограничения

- В БД пишет backend; расчёты денег, права и бизнес-переходы не переносятся во фронтенды. Форматирование и состояние интерфейса допустимы. [ADR-0002](decisions/0002-single-backend.md).
- Браузер общается через сервер своего приложения; сервисные токены остаются на сервере. Существующие различия авторизации описаны в [API](docs/api.md), их нельзя считать уже устранёнными.
- Схему ведёт Alembic backend. Применённые миграции и денежные события не переписываются. Баланс и выплаты — существующий payroll/earnings, без второго учёта.
- Оплата по ссылке связана с неизменяемым ID заказа. Время и имя клиента — контекст, не ключ сопоставления платежа. Новый контур пока тестовый: [статус](docs/current-state.md).
- Репозиторий публичный: не добавляй секреты, персональные данные, дампы, приватные документы сотрудников, логи с такими данными. Для частных подробностей оставляй ссылки.

## Перед изменениями

Проверь Git root, remote, текущую ветку, upstream, dirty-state и свежесть базовой ветки **в нужном репозитории**. Корень конкретного локального workspace может не быть Git-репозиторием. Чужие изменения сохраняй; работа — в своей feature-ветке/worktree. Определи поставщика API и всех потребителей изменения по [карте модулей](docs/modules.md).

Обычная сессия — разработчик. Можно выполнять порученную реализацию, локальные проверки, документацию, commit/push своей ветки и PR. Это не разрешение на мерж, теги, deployment, production SSH или изменение боевых данных. Полномочия релиза — только по уставу и явному решению владельца; старый локальный текст роли не расширяет их.

Изменения денежных правил, необратимые операции и архитектурные развилки проходят согласование по уставу. Не делай force-push, rebase/amend сданных коммитов, удаление данных/файлов без разрешения. Тестирование с изменением данных — в изолированном тестовом контуре. Наличие команды в runbook не даёт права её запускать.

## Перед сдачей

- Проверки выбранного продукта — [conventions.md](docs/conventions.md), его AGENTS и CI. Зелёные моки не доказывают работу с реальными данными.
- При изменении API/БД: проверить права, формы ответов, ошибки, потребителей, миграции и совместимость флагов. Денежные изменения — [money-dod](contracts/money-dod.md).
- Обновить контракт/документацию и CHANGELOG; для DOC выполнить `node scripts/check-docs.mjs` и `git diff --check`.
- Сдать свою ветку и PR с явной базой: что сделано, чем проверено, что осталось. Не объявлять прод готовым по факту merge, build или health 200.

## Как поддерживать DOC

Один факт — один основной документ, остальные ссылаются на него. [Реестр источников](docs/sources.md) хранит SHA и глубину просмотра. [current-state](docs/current-state.md) и [branches](docs/branches.md) — **датированные снимки**, а не мониторинг. При обновлении указывай дату, источник, способ проверки и её границы. Политику и наблюдаемое поведение не смешивать: код доказывает реализацию, но не меняет разрешения.
