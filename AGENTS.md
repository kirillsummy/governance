# SUMMY · DOC · вход для AI-агента

Governance — центральный DOC-репозиторий разработки SUMMY: продукт, карта реализации,
архитектура, межпродуктовые контракты и правила работы. Прочитай этот файл первым.
Это навигатор по конституции разработки; канон полномочий остаётся в [CHARTER.md](CHARTER.md).
Он не заменяется новым пересказом и не выдаёт разрешения на релиз.

## Вход за 5–10 минут

1. Этот файл и [current-state](docs/current-state.md): отличи основную ветку, feature и развёрнутый сервис.
2. [Продукт](docs/product.md) и [архитектура со схемами](docs/architecture.md).
3. [Репозитории и модули](docs/repositories.md): найди хозяина изменения.
4. Прочитай [устав](CHARTER.md), AGENTS.md выбранного продукта и его реестр DEBT.
5. По задаче: [API](docs/api.md), [БД](docs/database.md), [конвенции](docs/conventions.md),
   [инфраструктура](docs/infrastructure.md), [ветки](docs/branches.md), [ресурсы](docs/resources.md).

## Ограничения архитектуры

- Данные и бизнес-логика принадлежат backend. Фронты не подключаются к БД/S3
  с секретами и не считают начисления. BFF — серверная прослойка, не второй backend.
- Один журнал схемы — Alembic backend. Применённые миграции не переписывать.
- YClients ещё участвует в расписании, записи, идентификации сотрудников и зеркале;
  полный отказ от него не реализован. Не заменять зависимость молча.
- Деньги: фикс за услуги, не процент от чека; один источник начислений и выплат.
  Номер заказа и ID операции — ключи платежа. Возврат браузера не подтверждает оплату.
- Не выдавать демоданные, заглушку или выключенную функцию за рабочую интеграцию.
  Наличие кода и прохождение тестов не доказывают развёртывание.
- Привязка карты — требование владельца, пока не реализация в проверенном срезе.
  Не собирать PAN/CVV и не включать автоматическое списание по предположению.

## До изменений

Проверь git root, remote, ветку, upstream, dirty-state и актуальную базу на GitHub.
Не полагайся на имя локального каталога или устаревший origin/HEAD.
Работай в собственной feature-ветке/worktree. Соседние продукты — отдельные Git-репозитории.
Перечисли затрагиваемые читатели API/витрин; обновляй контракт вместе с реализацией.
Если меняешь только документацию, не запускай миграции или деплой ради её проверки.

Самостоятельно можно делать обратимые изменения в согласованной задаче, читать код,
обновлять документы и тестировать на выделенных локальных данных. Решения о новых
границах сервисов, втором денежном журнале, смене провайдера/стека, удалении данных,
правах, секретах и реальных платежах не принимаются из догадок: см. устав.

## До передачи

Проверь применимые [команды продукта](docs/conventions.md), совместимость потребителей,
ошибки и отключённые интеграции. Обнови CHANGELOG [Unreleased], документы и хендофф.
Коммит и push — только своей feature-ветки, PR с явной базой.
Готовые коммиты неприкосновенны: исправления новыми коммитами; без amend/rebase/force.
Мерж защищённых веток, теги и deployment выполняет релиз-инженер по процессу устава.
Наличие инструкции деплоя не даёт разработчику этих полномочий.

## Как обновлять DOC

Снимок в docs датирован **19.09.2026**. При обновлении укажи репозиторий, SHA,
проверенную часть и неизвестное. [Реестр источников](docs/sources.md) позволяет читать
точечно. Код доказывает поведение; устав и решение владельца определяют полномочия.
Старые ADR/контракты с уникальной информацией сохраняй; устаревшее помечай с причиной.
Governance публичный: не копируй секреты, клиентские данные, дампы и закрытые записи памяти.
Ссылки на приватные исходники требуют доступа GitHub и не делают их публичными.
