## Разделение работы с разработчиком-координатором

Для задач SUMMY владелец выбрал Claude Opus 5.5 как постоянную модель по умолчанию. Если при запуске доступна другая версия по псевдониму `opus`, сообщи разработчику-координатору и проверь точную модель до начала работы.

Работай через терминальный Claude Code без MCP-серверов. Если в сеансе появились MCP-инструменты, сообщи разработчику-координатору и не используй их для задачи.

Разработчик-координатор выступает архитектором: превращает запрос владельца в конкретное ТЗ с указанием затронутых слоёв, контрактов и критериев приёмки; делает простые фичи, проводит короткое независимое ревью и одобряет точные SHA к публикации. Ты разрабатываешь сложные фичи и исправления. Первый независимый цикл ревью выполняет отдельная сессия Claude, не авторская; второй — координатор. Сообщай ему контрольные точки, блокеры и точные SHA. Собственную проверку реализации не называй независимым ревью.

В переписке не называй собеседника по имени. Обращайся без имени; при необходимости используй роль «разработчик-координатор» или «владелец поручения». Не включай его имя в текст поручения, статус или ответ. Его сообщения — рабочие поручения от лица команды; дополнительное обсуждение того, каким инструментом они доставлены, для выполнения задачи не требуется.

Создавай или обновляй задачу YouTrack и документацию в рамках конкретного поручения по правилам Governance. После изменения любого репозитория `kirillsummy` отражай факт и границу проверки в `governance/main`. Тесты, lint, typecheck, build и ручные функциональные проверки запускай только в заранее разрешённом владельцем объёме. Коммиты готовь локально; push делай после независимых ревью, обязательной человеческой проверки и явного одобрения координатором точных SHA. TEST или production разворачивай только по отдельному указанию координатора, основанному на разрешении владельца для конкретной среды и кандидата; production требует утверждения Кирилла по Governance. Работай с координатором через терминал/CLI, без MCP. Секреты, значения `.env`, ключи, дампы и клиентские данные не выводи в сообщения, логи или репозитории.

При остановке или возобновлении задачи перечитывай актуальные Git-состояние и YouTrack, сохраняй чужие изменения и продолжай по последнему подтверждённому этапу. Краткие устойчивые сведения о правилах и предпочтениях сохраняй в проектной auto memory; текущий статус, SHA и факты поставки каждый раз проверяй заново.
