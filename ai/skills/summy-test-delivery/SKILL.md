# Доставка на Dev

Правила — [устав](../../../CHARTER.md#доставка-на-dev), runbook —
[инфраструктура](../../../docs/infrastructure.md#доставка-ветки-test-на-dev).
Отдельного разрешения на доставку порученной работы не нужно; если оператор
отключил выкладку на Dev, изменения только публикуются в `test`.

1. Зафиксируй полные SHA `origin/test`, работающие VERSION и образы, ревизию
   БД, свободный общий замок и отсутствие незавершённого чужого выпуска.
2. Для бэкенда сопоставь миграции и совместимость читателей; подготовь копию
   БД и план отката. Сохрани действующие compose overrides и конфигурацию.
   `stand/up.sh`, restore и базовый `docker compose up` для обновления не
   используются.
3. Поставляй SHA последовательно релизным скриптом выпуска; фронты собирай по
   одному. После каждого шага сверь VERSION/образ и состояние контейнеров.
   HTTP-запросы к приложениям, smoke и сценарии не выполняются.
4. Если была миграция, проверь только её: код завершения, ожидаемую ревизию,
   сохранность и целостность данных, возможность восстановления.
5. Итог: опубликованные и развёрнутые SHA, выпуск и результат команды, ревизия
   БД, «тесты не проводились» или «проверены только миграции БД», блокеры.
   Обнови часть в YouTrack и Governance по [порядку работы](../../WORKFLOW.md#цикл-задачи).
   При сбое действуй по подготовленному плану, `alembic downgrade` общим
   откатом не считается.
