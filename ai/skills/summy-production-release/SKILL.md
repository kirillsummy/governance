# Релиз Prod

Правила — [устав](../../../CHARTER.md#релиз-prod), шаги —
[порядок работы](../../WORKFLOW.md#релиз-prod), доступ и бэкапы —
[инфраструктура](../../../docs/infrastructure.md#prod). Релиз проводит
участник с действующим доступом к Prod по поручению любого участника
команды; отдельного личного утверждения и одобрения номера кандидата нет.

- **Кандидат** снимается с работающих артефактов Dev, а не с головы `test`:
  VERSION и метки ревизии образов, ревизия БД, полные SHA. Release-карточка
  перечисляет части, SHA, миграции «с → на», флаги без секретов, копию и откат.
- **Проверки** затронутого на точных SHA в изолированных рабочих каталогах.
  Ошибки продукта и устаревшие тесты исправляются в `test`, затронутое
  прогоняется повторно до зелёного результата. Миграции репетируются на копии
  БД Prod. Красный кандидат не выпускается; сравнение с красной базой его не
  оправдывает.
- **Перед переключением:** версии Prod против тегов и production-веток,
  совместимость миграций и читателей, место на диске, свежая копия БД,
  свободный замок. Production-БД — отдельная управляемая PostgreSQL;
  реквизиты Dev не переносятся.
- **Выкладка** ровно кандидата по продуктовым runbook; после — версии,
  ревизия БД, состояние сервисов. При сбое — заранее подготовленный откат,
  без слепого downgrade схемы.
- **Фиксация:** production-ветка → выпущенный SHA без force, тег,
  документ выпуска в `docs/releases/`, CHANGELOG, текущее состояние,
  release-карточка и стадии частей; исправления подготовки — на Dev без
  дополнительных тестов. Поставленный выключенным код функцию не включает.
